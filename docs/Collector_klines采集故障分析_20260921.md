## 0. 先校验前提（重要：本轮"故障"的表述有错前提）

用户措辞"collector/klines 采集故障"隐含两个前提，逐一核对：

| 隐含前提 | 核实结果 | 证据 |
|---|---|---|
| (A) `hcm-collector` 容器是 K 线生产写入方，且当前宕机/异常 | **不成立**。生产 K 线写入方是**宿主机进程 `mt5_bridge.py`**，不是容器。collector 的 `pg_write_enabled` 在生产被刻意关闭（避免双写）。 | `hcm-collector/collector/kline_collector.py:188/362`（`self._pg_write_enabled`）、`:377` 注释"当前虽未在写行情库"；`mt5_bridge.py:3510-3528` 主号写库、`:3527` 从号跳过写库 |
| (B) 采集目前处于"中断/坏掉"状态，需要重启修复 | **不成立**。断流是**历史窗口**（09-20 00:07:46 → 08:16:08，约 8h8m），08:16 已被 launcher/watchdog 自恢复；桥进程**当前在线**（最新写库 09-21 17:09:52，持仓同步 09-21 17:10）。 | 见 §1 时间线 |

**结论**：不存在"现在要重启 collector 修复采集"的合理性。盲目重启当前健康的容器/桥反而有风险（重启健康组件、可能触发双写、打断在跑的持仓同步）。真正要做的是：(1) 复盘 09-20 断流的**根因**并**加固可靠性**，避免再静默断 8 小时；(2) 关闭两个**独立的数据缺口**（M15 空表、09-20 历史缺口）；(3) 处理**噪声/配置漂移**（misaligned 刷屏、缺失配置键）。

## 2. 09-20 断流根因（事实 vs 推测）

**已确证的事实**
- 主号桥进程在 09-20 00:07:46 后**整进程停止/静默**（连持仓同步都停），08:16:05 才被重启。
- 断流前**没有任何 ERROR / Traceback / Exception 日志**（08:16 之前的 09-20 日志中唯一 ERROR 是 08:16:31 的配置缺失，属重启后；MT5 断开是 09:07，也晚于重启）。即：**桥是"静默死亡/卡死"，未留崩溃原因**。
- 恢复由 `start.bat` 的 `launcher → watchdog → mt5_bridge` 链（start.bat:281, :340）完成，但**花了约 8 小时**——说明该看门狗要么只捕获"硬退出"不捕获"活着但死循环/僵死"，要么看门狗自身那段时间也不可用（宿主机层面问题）。

**合理的推测（标注为未证实）**
- 推测 a：宿主机/launcher 在 00:07~08:16 期间不可用（如 Windows 会话结束、Docker Desktop 或终端宿主异常），导致桥无人拉起。
- 推测 b：桥主循环某处未加超时/异常兜底，遇到 MT5 返回的异常数据或网络抖动后**整进程僵死**，而非退出，看门狗（仅监测进程退出）检测不到。
- 以上两条都无法从现有日志坐实（无崩溃栈），需查宿主机事件日志 / launcher 日志才能定论。**不把推测当结论。**

**监控盲区（关键系统性缺陷）**
- 桥内部**没有"写库心跳/存活断言"**：K 线循环卡死或进程僵死，桥自己不报警。
- signal-tower 的 feed-stale 探测器（600s 未更新即 `ALERT kline feed STALE … Pausing signal production`）**只暂停信号生产，不升级、不重启桥、不通知运维**。于是 8 小时断流在运维视角只是"信号暂停"，极易被忽略。
- 结果：一个本应分钟级自愈的故障，拖成 8 小时静默断流，并间接造成上一轮的 PSI 重度漂移误报（见关联文档）。

## 3. 误报/无关项：misaligned 警告是噪声，不是断流原因

`K-line open_time misaligned (XAUUSD H4/D1)` **每天都在刷**，数量巨大：

| 日期 | H4 条数 | D1 条数 |
|---|---|---|
| 09-14 | 12403 | 11607 |
| 09-15 | 21824 | 16410 |
| 09-17 | 14128 | 14113 |
| 09-20 | — | — |
| 09-21 | 11851 | 11842 |

- **根因（良性）**：`mt5_bridge.py:548-552` 说明经纪商 UTC 偏移不是 H4(14400s)/D1(86400s) 的整数倍，落地 open_time 偏离 UTC 网格，桥做"圆整/snap"。M5/H1 因能整除 3600 而自动对齐，所以**只有 H4/D1 报警**，且**与 M5 断流无关**（M5 在 09-20 断流窗口外的其他时段照常写库）。
- **但它是真问题**：单日志已 177MB；每日 1~2 万条 WARNING 既**刷屏淹没真实 ERROR**，又会让运维对 WARNING 麻木——若将来出现**真的**错位反而看不见。需降噪（见 §5 P2）。

## 4. 两个独立的可靠性/配置问题

**(a) 反复 MT5 终端闪断**：09-09 与 09-20 09:07 均出现 `positions_get() returned None (MT5 disconnected?)` 的秒级爆发（数百条）。这是经纪商/终端连接不稳定，非代码 bug，但桥在断开期间跳过持仓同步，存在漏同步窗口。需确认终端自动重连机制是否够稳。

**(b) 缺失配置键（配置漂移）**：09-20 08:16:31 `REQUIRED close config 'state.trend.min_sl_atr' missing in Redis/PG — using fallback 0.30`。项目铁律"禁用硬编码"下，这等于一个**必需配置没进 Redis/PG**，桥退化为硬编码 0.30。属配置不一致，应把该键写回 `hcm_config.config` + Redis `hcm:config:v2`。

## 5. M15 空表：独立的配置缺口（不是崩）

- 事实：`hcm_market.klines_xauusd` 的 **M15 = 0 行**。`mt5_bridge.py` 日志中 "M15" 出现 **0 次**。
- 桥**支持** M15（`TIMEFRAME_MAP:314`、`MT5_TIMEFRAME_MAP:318/472`、`TF_SECONDS:542` 都含 M15），但采集循环 `all_timeframes = mt5_cfg.get('timeframes', [timeframe_str])`（`mt5_bridge.py:3496`）的部署配置 `timeframes` 列表**漏了 "M15"** → 从不采集。
- **对 XAUUSD 当前影响：低**。XAUUSD 主周期 = M5（`scheduler.py:318` `DEFAULT_TIMEFRAMES={"XAUUSD":"M5",…}`）；`scheduler.py:6077` 的 `tf_chain=(H1,M15,M5)` 中 M15 只是中间兜底，H1/M5 都在，故 M15 缺失不阻断 XAUUSD。
- **潜在风险**：`BTCUSD` 默认 M15（`scheduler.py:318`），虽生产未启用；且任何显式需要 XAUUSD M15 棒的特征/逻辑会读到空数据。属于**潜伏缺口**，建议关闭或显式书面认定"故意不采"。

## 6. 分级修复方案（均需在授权后执行；生产写/重启须逐条确认）

### P0 — 可靠性：杜绝"静默断 8 小时"（最高优先）
1. **桥内写库心跳 + 看门狗联动**：在 `mt5_bridge.py` K 线循环加"最后成功写库时间"记录；看门狗（或独立 monitor）检测到 > N 分钟（建议 10min）无写库 → **强制重启桥 + 发运维告警**。解决"僵死但进程在"的盲区。
2. **signal-tower feed-stale 升级**：当前只暂停（`scheduler` 的 STALE 分支）。改为：暂停的同时**发告警并尝试拉起桥**（或至少通知运维），避免 8h 无人知。
3. **宿主级保活**：确认 `launcher→watchdog` 链在宿主机异常时也能恢复；必要时加 Windows 任务计划程序的健康探活，避免宿主问题导致桥裸奔 8h。

### P1 — 数据完整性
4. **回填 09-20 00:07~08:16 缺口**（XAUUSD M5/M1/M30/H1/H4/D1，从 MT5 历史回拉）。属 **PG 写入（生产数据改动）**，须显式授权。权衡：缺口已历史，回填能还原该窗口 PSI/特征准确性，但推理已用过坏数据（见 PSI 文档），是否回填需你定夺。
5. **关闭 M15 缺口**：把 `"M15"` 加入 `mt5_cfg['timeframes']`（Redis/PG 配置），桥即开始采集。配置变更，须授权；对 XAUUSD 风险低。

### P2 — 降噪 / 配置卫生
6. **misaligned 降噪**：修正 `broker_utc_offset_s` 处理使 H4/D1 落 UTC 网格，或将该 WARNING 降级为 DEBUG / 限频。否则持续膨胀 177MB 日志并淹没真错。
7. **补配置键**：将 `state.trend.min_sl_atr` 写入 `hcm_config.config` + Redis `hcm:config:v2`，去除硬编码 fallback 依赖。

### P3 — 复核
8. **核对 collector 容器状态**：本会话 `docker ps` 在沙箱内无返回（Docker daemon 不可达），未能复核；请在宿主确认 `hcm-collector` 实际状态，并确认其 `pg_write_enabled=false`（防止双写）。
