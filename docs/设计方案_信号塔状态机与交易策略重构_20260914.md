## 1. 架构分层

```
L1 特征层   state_features.py      单一真值契约（训练/推理同源，禁止双份实现）
L2 模型层   lgbm_state_{M5|M15|H1}_v{N}.txt  三套独立模型（禁止跨周期混用）
```

## 2. 补全规格空白：4 类标签口径（方案核心）

用户只给了类别名，未给可计算定义。以下为建议口径（**阈值全部由数据分位数标定，不拍脑袋**）。

### 2.1 记号

取主周期已收盘 bar `t`，`ATR_t = ATR(14)`，未来窗口 `W = [t+1 .. t+N]`，`N = state.horizon_bars[tf]`（用户区间 10–20，建议初值 12）。

```
Δ      = close[t+N] − close[t]
P      = Σ_{i=t+1..t+N} |close[i] − close[i−1]|
ER     = |Δ| / max(P, ε)                     # Kaufman 效率比 ∈[0,1]
disp   = |Δ| / ATR_t                         # ATR 归一化净位移
mid    = t + ⌊N/2⌋
ER2    = |close[t+N] − close[mid]| / P2      # 后半程效率比
disp1  = |close[mid] − close[t]| / ATR_t
disp2  = |close[t+N] − close[mid]| / ATR_t
ADX_slope = ADX(t+N) − ADX(t)
MAE    = 窗口内最大逆行 / ATR_t  ;  MFE = 窗口内最大顺行 / ATR_t
newExt = 窗口内是否顺向创 lookback 窗口外新高/新低
```

### 2.2 类别判定（互斥，**优先级从上到下**）

| 序 | 类别 | 条件（建议初值） | 语义 |
|---|---|---|---|
| 1 | `oscillation` | `ER ≤ er_osc` **且** `disp ≤ disp_osc` | 往返无净位移 |
| 2 | `trend_fade` | 非 1，且 `ADX_t ≥ adx_trend` 且 `ADX_slope ≤ −adx_slope_min` 且 (`ER2 ≤ er_fade` 或 `MAE ≥ fade_ret_atr`) 且 `not newExt` | 未来窗口内趋势停止/反转 |
| 3 | `trend_init` | 非 1/2，且 `disp1 ≤ disp_init` 且 `ER1 ≤ er_osc` 且 `disp2 ≥ disp_min` 且 `ER2 ≥ er_trend` | 前段静、后段动（启动点） |
| 4 | `trend_mid` | 其余（`ER ≥ er_trend` 且 `disp ≥ disp_min`） | 趋势延续中段 |

**说明**：类别**不含方向**。方向由 L1 特征层的线性回归斜率在推理时实时判定
（与用户 10.1「斜率 > 0 = 多头趋势」一致）。

### 2.3 置信过滤（剔除，不参与训练 —— 对应需求二.2）

剔除条件（任中其一）：
- 边界带：`|ER − er_osc| < er_band`、`|disp − disp_min| < disp_band`、`|ER2 − er_trend| < er_band`
- 半程分类与全程分类冲突
- 二义性：首轮模型训练后回看，`top1_prob − top2_prob < margin` 的样本，v2 迭代再剔
- 复用 `build_labels.py` 已有硬剔除：跳空（`gap_skip`）、重大事件窗口（`event_skip`）、未来窗口不足
- **保留但降权**（不剔除）：类别不平衡用 `sample_weight` 处理，见 §4

### 2.4 阈值标定流程（禁止硬编码）

1. 在训练集上取分位数给初值：`er_osc≈p30`、`disp_osc≈p25`、`disp_min≈p45`、`er_trend≈p60`、`disp_init≈p30`、`adx_trend≈p55`
2. 网格搜索（含 `N ∈ {10,12,15,20}`）以「4 类可分性（宏平均 F1 / AUC-OVR）+ 时序 CV」为目标
3. 标定结果落配置中心 `state.label.*`（PG + Redis 双写），训练与离线评估可复现
4. 离线评估报告须给出：类别分布、时序 CV 宏 F1、混淆矩阵、`trend_fade` 召回（用户重点关注）

## 5. 推理与校验（L3）

1. 输入：品种 + 主周期已收盘 K 线序列
2. 特征计算：调用 `state_features.compute(...)`（与训练同源）
3. **特征校验**：空值 / 非有限值 / 超出训练基线 z 阈值 → 判推理失败
   - ⚠️ **建议细化分级**（用户原文为"失败→S9"，过于激进）：
     - 单根异常 → **保持上一状态不切换** + 告警（避免一根脏 bar 就停策略）
     - 连续 `state.infer_fail_bars` 根异常 → 进 **S9**
4. LightGBM 推理（K 模型概率平均）→ 4 类概率
5. 单 K 判定：`argmax`
   - ⚠️ **建议补充**：若 `max_prob < state.min_conf` 则该根**不参与防抖**（视为"未判定"），
     而非强制切换类别——这是防抖之外的第二道抗噪
6. 输出原始判定 → 防抖模块（§6）

| 状态 | 允许动作 | 方向来源 | 手数 | SL | TP |

### 7.1 箱体锚定规则（对用户规格的关键补全）

用户规格「箱体上沿 = 窗口内最高价」，若窗口**含当前/滚动** bar，则：
1. 价格永远碰不到 `≤ 下沿`（下沿随价格下移）→ 入场条件退化；
2. 开仓后 `箱体中值` 随价格滑动 → **止盈目标失效**。

**补全建议**：
- 箱体用「截至上一根已收盘 bar」的回看窗口计算（滚动，用于**入场判定**）
- **开仓瞬间冻结箱体**（upper/lower/mid 快照），本轮 TP = 冻结 mid，直到本轮结束（止盈/止损/状态切换）才重算
- 冻结快照落 Redis `hcm:state:box:{symbol}:{direction}`
- 该规则使「箱体内部禁止开仓」可判定：`box_lower < price < box_upper` → 不开仓

### 7.2 加仓（金字塔）与风控的关系

- 风控 `risk.max_concurrent_signals`（生产 =3）按**总持仓数**封顶 → 会拦掉第 2、3 笔加仓；
  且 `_check_cooldown` 同向持仓时间窗也会拦同向加仓。
- 因此 **加仓必须走独立语义**（`action=add`）并在风控侧显式豁免（仅对 `state_fsm` 模式 + 同向 + 未超 `max_adds`），
  否则趋势加仓在生产环境**根本不生效**。→ 决策点 Q5 的连带项，必须一并定。

## 8. 持仓管理层（L7）—— 最高优先级决策点

新方案要求的持仓管理与现状**冲突**：

| 需求 | 现状 | 冲突 |
|---|---|---|
| S3 移动止损 = 近 N 低/高 ∓ ATR×k，只前移，触碰**全平** | 桥 `_update_trailing_stops` 会话化 breakeven/trail_start/tp_relay，**逐仓 SL 前移**，不主动全平 | 两套 SL 逻辑争控制权（历史同类事故：跟单桥自管 trailing 与主号镜像争 SL） |
| S1 TP = 箱体中值 | 桥用 `zone_tp_level` / 会话 TP 倍数 | 需透传冻结 mid |
| S3 顺势加仓 | 桥按信号开单，无"加仓"语义 | 需 `action=add` 全链路支持 |
| S4 只持有 | 桥不区分状态 | fsm magic 需豁免桥 trailing（否则桥会收紧 SL） |

**三个候选（决策点 Q5）**：
- **甲（推荐）**：桥新增按 `signal_mode/magic` 分流的 FSM 管理分支 —— 桥持有实时 tick 与持仓访问权，
  与现有「主号自管 trailing」同构；改动集中在桥，信号塔只下发意图（状态 + 箱体快照）。
  代价：桥是主机进程，改动需 kill + 看门狗重拉（需安全时段）。
- **乙**：信号塔每根 bar 计算并下发 `MODIFY` / `ADD` 信号，桥不改；
  但**必须禁用桥对 fsm magic 的 trailing**（否则双头管理），且依赖现有 `manual mirror` MODIFY 链路。
- **丙**：混合——开仓/加仓由信号塔信号驱动，SL/TP 由桥。

## 11. 风险与回滚

| 风险 | 说明 | 缓解 |
|---|---|---|
| 标签口径主观 | 4 类阈值若拍脑袋 → 模型学不到稳定结构 | 全部走分位数 + 网格搜索；离线报告留证 |
| train/serve 特征漂移 | 训练/推理两份实现 → 分布不一致 | 单一真值文件 + 推理侧列名校验（fail-fast） |
| 闭环自回归特征 | `prev_state_*` 训练用真实标签、推理用预测 → 漂移 | 见 Q8，建议首版不用 |
| 箱体滑动 | 入场/止盈失效 | §7.1 冻结箱体 |
| 与 hexp 双头裁决 | 方向互相打架 | 明确单一裁决权（Q1） |
| 风控拦截加仓 | 趋势加仓不生效 | §7.2 独立 add 语义 + 显式豁免 |
| 桥 trailing 冲突 | SL 争控制权（历史事故） | §8 明确执行方 + 豁免规则 |
| 锁止/计数器丢失 | 重启后重复开仓 | Redis 持久化 + 平行落 PG |
| 过度暂停 | 单根脏 bar 即 S9 → 长期不交易 | §5 分级 + 连续失败才 S9 |
| **回归**（铁律第十一章） | 新代码误伤 hexp / 风控 / 桥 | 影子先行；不触碰 hexp 方向裁决直到 Q1 确认；桥改动单独窗口 + 备份 |

**回滚**：所有新增模块可 `state.enabled=false` 秒级关闭；桥改动保留 `.bak` + 单分支开关；配置键可回退。

## 12. 与现有机制的红线冲突（必须裁决）

1. **方向裁决权**：新 FSM 直接产出方向（趋势顺势 / 震荡逆势）↔ hexp 7 因子 `dir_sum`。
   两者不能同时决定方向 → **Q1**。
2. **止损执行权**：桥 `_update_trailing_stops` ↔ FSM 移动止损 → **Q5**。
3. **评审器 / quality_gate**：新信号是否仍经 `reviewer` / `quality_gate`？
   （建议：影子阶段**只观测**，灰度阶段保留评审器但在 FSM 决策**之后**做二次否决 → 待确认）
4. **signal_mode / magic**：需新增 `state_fsm` 及子模式（`state_osc` / `state_trend`），
   `magic_for_signal_mode` / `SIGNAL_MODE_MAGIC` 需同步扩展（`signal_publisher.py`）。
5. **4ATR 计数器数据源**：止损成交事件回传——现有 `position_sync._infer_close_reason`
   （`deal.reason=4`）已能识别 SL，可直接复用为计数触发源（无需新通道）。

## 20. 方向裁决改为规则模块 + FSM 组合规则（2026-09-15）

### 20.1 用户规格（本次裁决口径）

方向由**独立指标模块**判定（不再是模型，也不再是 hexp）：

| 方向 | 条件 |
|---|---|
| `UP` | 斜率 > 阈值 **且** +DI > −DI |
| `DOWN` | 斜率 < −阈值 **且** −DI > +DI |
| `NONE` | 无明确单向趋势（方向模糊） |

FSM 同时接收【LGBM 防抖后的**形态**】与【**方向**】联合决策：

| 形态 | 方向 | 行为 |
|---|---|---|
| oscillation | 忽略 | 箱体震荡策略 |
| trend_init | UP/DOWN | 允许顺势回调开仓 |
| trend_init | **NONE** | **禁止趋势开仓** |
| trend_mid | UP/DOWN | 允许顺势开仓与加仓 |
| trend_mid | **NONE** | 禁止新增，**已有持仓继续持有** |
| trend_fade | 任意 | 禁止新增；持仓**收紧移动止损**，准备离场 |

> 约束：形态判趋势但方向 NONE → 不开趋势仓（规避方向模糊的假趋势）。

### 20.2 落地实现（`signal_tower/trend_direction.py`，新增）

工程补全两处（规格未明确但必需）：

1. **阈值必须 ATR 归一**。原始斜率单位「价格/根」随品种价位量级变化（XAUUSD≈2000 与
   EURUSD≈1.08 相差千倍），照字面配置斜率阈值换品种即失效。故定义为
   `slope_atr = slope_raw × slope_window / ATR`（= 回归趋势线在窗口内的总位移是几个 ATR，
   无量纲），配置键 `state.dir.slope_thr_atr` 以此为单位。
2. **防抖做成"无状态纯窗口函数"**：`confirmed[i] = raw[i]` 仅当最近 k 根 raw 全等，
   否则 `NONE`（键 `state.dir.debounce_bars`）。不用"带 carry 的迟滞"是因为那是有状态
   逻辑，离线整段与线上增量在起点不同时会分叉（本仓库历史事故类型）→ 纯窗口函数 ⇒
   **离线标签与线上推理逐点相同**。

**单一真值**：斜率直接调用 `state_features._linreg_slope_r2`，**不写第二份实现**。
自研 O(n) 前缀和版实测相对偏差 **3.96e-06**（根因：`Σ j·y` 在 n≈2e4、price≈2000 时量级
达 1e10，相邻窗口相减灾难性抵消），中心化只能缓解不能根除 → 删除该版，与契约
`slope_linreg` **同源同值**（自检实测最大偏差 **0.00e+00**，见
`tools/eval_trend_direction.py --no-selfcheck` 可跳过）。

### 20.4 口径对照：`state_strategy` 斜率裸符号 vs `trend_direction` 规则模块

**两者用的是同一个斜率**：`scheduler.py:1989` 传 `infer.feats["slope_linreg"]`，即
`state_features` 的 `slope_raw × slope_window / ATR` —— 与本模块 `slope_atr` 同源同值
（自检偏差 0.00e+00）。故差别**不在归一化尺度**，只在四项：阈值 / ±DI 确认 / K 线防抖 / NONE。

实测（XAUUSD M5，20288 根，前视 N=12，`--compare` 模式）：

| 维度 | A) 现状：斜率裸符号 | B) 规则模块 |
|---|---|---|
| 输出状态 | 恒 `up`/`down` | `up`/`down`/`none` |
| 分布 | up 48.2% / down 51.8% / **none 0%** | up 12.3% / down 14.5% / **none 73.2%** |
| 切换率 / 平均同向持续 | 0.053 / **18.94 根** | 0.051 / 19.77 根 |
| up 组位移均值 | **−0.0003**（≈无信息） | +0.0932 |
| up 组上涨占比边际 | −1.46pt | −0.70pt |
| down 组位移均值 | **+0.0401（反向）** | **+0.1353（更反向）** |
| NONE 组 \|位移\| | — | 0.788（基线 1.010）✓ |

**一致性（关键）**：规则断言方向的 bar 中，与裸符号**方向相反 = 0.0%**。

的 `slope>0` 同号）。规则从不给出与裸符号相反的方向。

**结论（三条，均有实测支撑）**：

1. **规则模块的实质增量只有"NONE"这一项**：73.3% 的时间拒绝表态，且这些 bar 的
   \|位移\| 0.788 明显小于无条件 1.010 → 确实筛掉了"没行情"的时段。
2. **别指望规则模块"修正方向"**：up 侧边际仅从 −1.46pt 收窄到 −0.70pt；
   **down 侧反而更差**（+0.0401 → +0.1353），且筛出的 bar 波动更大（\|位移\| 1.57 vs 1.02）
   —— 方向反 + 波动大 = 亏损放大。
3. **我先前"裸符号会高频跳变、每根 bar 都可能翻向"的推断是错的**：
   实测平均同向持续 **18.94 根 bar**（切换率 5.3%）。原因：20 根重叠窗口的回归斜率变化平滑。
   按铁律第十二章更正 —— 该论断无数据支撑，撤回。

**对修复方案的含义**：把策略层符号换成规则符号，**几乎不改变方向行为**（100% 同向），
主要效果是让 73% 的 bar 变成"不开仓"（降风险，但交易数大减）。**方向符号本身的问题
（down 侧反向）两种口径都没解决** → 更支撑 §20.5 的选项 A（M5 只授权 NONE 否决）。

### 20.5b 谁更"贴合实时行情"：与**形态真值**交叉（2026-09-15）

判据（避免循环论证）：一个"贴合行情"的方向模块应当**知道何时不该有观点** ——
震荡形态下多说 NONE，趋势形态下才断言 UP/DOWN。

| 形态 | n | A 断言率 | A up 占比 | B 断言率 | B none 率 |
|---|---|---|---|---|---|
| oscillation | 4830 | **100.0%** | 47.9% | **17.1%** | 82.9% |
| trend_init | 1357 | **100.0%** | 44.7% | 34.9% | 65.1% |
| trend_mid | 4389 | **100.0%** | 48.4% | **29.8%** | 70.2% |
| trend_fade | 1270 | **100.0%** | 51.8% | 44.2% | 55.8% |

**滞后代理**（trend_mid 刚进入后 B 的断言率；A 恒 100%）：前 1–3 根 31.9% /
第 4–9 根 28.5% / 第 10–30 根 37.1%（737 次进入事件）→ **无明显滞后**。

**裁决：B（规则模块）更贴合，但幅度有限。**

1. **A 是结构性硬伤**：断言率恒 100%、up 占比在 44.7%~51.8% 徘徊 → **零区分度**。
   在 4830 根真·震荡 bar 上它照样输出"有明确方向" → FSM 会据此开趋势仓。
2. **B 的区分度正确但偏弱**：震荡 17.1%（最低）✓、衰竭 44.2%（最高）✓，
   但 **trend_mid 29.8% 低于 trend_init 34.9%**（逻辑上应相反）→ 趋势中段断言率仅
   ~30%，作为趋势方向门会**漏掉 >70% 的趋势 bar**；震荡下仍留 17.1% 假阳性。
3. **B 的优势不在"更准"，而在"敢拒答"**：其断言率随形态变化、且 NONE 组 \|位移\| 显著更小
   （§20.4）。
4. **必须扣掉的错配**：形态标签是**前视**（由未来 12 根定义），方向模块是**后视**指标 ——
   一根"事后才成为 trend_mid"的 bar，其过去 20 根未必像趋势。故 B 的弱区分度里有
   **不可消除的检测滞后成分**，不能全记在 B 头上。A 的零区分度则无可辩解。

## 21. 验收门：状态模型有没有解决"指标滞后"？→ **未达成**（2026-09-15）

用户要求（原话）：*"LightGBM 状态机推理预测要解决指标滞后问题，这是必须的，必须敏锐捕捉行情变化"*。

### 21.1 三个必须记录的事实

1. **一条朴素 Donchian 突破规则全面胜过 27 特征 LGBM**：更早（中位 −4.0 vs +3.5）、
   零漏检（0 vs 20%）、误报率 1/7（9.9% vs 67.8%）。
   —— 但须公平指出：donchian 是**针对性极强的二值门**，而模型被迫在 4 类里 argmax，
   两者任务不完全对等。它证明的不是"规则更聪明"，而是**"趋势是否开始"这个二值判断在本
   数据上有简单可靠解法，而当前 4 类 argmax + 保持前值链路把这份可靠性丢掉了**。
   注意 `box_break_up/dn`、`new_high_cnt` 本来就在特征里 —— **信息不缺，是决策规则丢了敏锐度**。
2. **「低置信保持前值」是自伤**（可隔离、可修）：仅把该语义改为"低置信→震荡"，
   漏检 20%→1.8%、中位 +3.5→−0.5 bar、误报 67.8%→52.2%。这一项就吃掉约 4 根提前量。
3. **`adx_rule` 基线存在循环引用**：ADX 是标签构造阈值之一（`state.label.adx_trend`
   用于 trend_fade 判定），故其"时间贴合度"被系统性高估（中位 +0.0 是假象）。
   换非循环基线后结论由"略差"变为"差 7.5 根"。**基线选择直接改变结论**，故必须用非循环基线。

### 21.2 病因与修复方向（按证据强度排序）

| # | 病因 | 证据 | 修复 |
|---|---|---|---|
| 1 | FSM「低置信保持前值」导致状态黏滞 | §21.1 第 2 条（遗漏/误报/提前量三项同向改善） | 改为"趋势态需持续置信支撑，否则衰减回震荡"（**核心机制变更，需出变更说明**） |
| 2 | 用 4 类 argmax 直接当"趋势门" | 误报 67.8% vs Donchian 9.9% | **把"是否进入趋势族"从 4 类里解耦**：独立二值门（或用 1−P(osc) 阈值）决定"是否趋势"，4 类继续负责**细分** init/mid/fade |
| 3 | `trend_init` 单类 F1 仅 0.1226（S2 无法触发） | Phase A OOF 指标 | 需确认是标签口径（N=12 前视 + 置信过滤后样本 1331）还是特征不足 |

### 21.3 样本局限（如实标注）

样本外段仅 2378 标注 bar、**55 次切换事件**；中位数基于 44~55 个事件 → **统计强度中等**，
结论方向可信、具体根数有波动。M15 仍无数据（L5）。

## 23. 数据驱动的状态发现：**可学性大幅改善，但"初生 vs 中段"仍不可学**（2026-09-15）

用户要求：*"必须让状态机自主学习，具备不同周期的状态识别能力"*。

**做法**（`tools/discover_state_labels.py`，新增）：不再人工写阈值定义状态，改为
**未来路径签名向量**（11 维连续统计量、零阈值）上做无监督聚类（GMM），再用 LGBM 学
「当前特征 → 簇」。状态边界由数据决定。

### 23.1 第一次迭代就否掉了一个陷阱，也暴露了方向污染

- **陷阱（必须先说清）**：若对**当前特征**聚类当标签，LGBM 会完美拟合聚类边界（F1 虚高），
  但状态退化成过去的确定性函数 → **提前量归零**，等于再造一个滞后指标。
  故签名必须建在**未来**路径上（编码未来才有提前量）。
- **首版实测**：签名含带符号 `fwd_ret`/`fwd_slope` 时，k=4 的簇是
  「c1: net=**+1.156** 强上涨 / c3: net=**−1.387** 强下跌 / c0: net≈0 / c2: 扩张启动」
  → **簇结构被"方向"主导，而非"阶段"**，自动命名把强上涨簇误命名为 oscillation。
- **修正**：签名**去方向化**（取绝对值）。理由：本方案架构里方向已由 `trend_direction`
  独立负责，状态只需描述形状/阶段；把方向塞进状态标签既与方向模块冲突、也让状态不可解释。

### 23.4 由此得出的设计结论（**建议，待裁决**）

> **状态标签不应按"幅度分层"，而应按"形状/方向性推进是否成立"定义。**

- 幅度（1.3 vs 4.0 ATR）不可预测 → 把它做成分类类别，注定不可学；**幅度应留给仓位管理**。
- "初生"的敏锐性应由**触发器**承担：**当前处于压缩状态**（过去可观测）+ 突破确认，
  而不是由一个「未来幅度很大」的类别承担。
- 落到类别数：建议 **3 类形状**（`oscillation` / `trend_progress` / `trend_exhausted`）+
  **独立的方向模块** + **独立的启动触发器**。这样每一块都建在**可观测/可预测**的量上。

## 24. 三件套落地：3 类形状怎么分（2026-09-15）

用户决策：*"把'四阶段'改成「3 类形状 + 方向 + 触发器」三件套"*。

### 24.1 划分原则（两条硬约束）

1. **尺度无关**：形状只描述"路径长什么样"，不描述"走了多远"。故聚类空间**剔除全部绝对
   幅度维**（\|净位移\|/总路径/最大有利偏移/最大不利偏移/\|斜率\|），只留 7 个比值或窗口内
   相对位置维（`SHAPE_COLS`）。理由：§23.3 已证"行情多大"不可学（init vs mid AUC 0.588），
   把幅度留在聚类空间里，k=3 必然又按大/中/小分层，得到的仍不可学。**幅度交仓位管理。**
2. **按时间结构分**：三类必须能由**未来窗口内部的时间结构**区分，而不是只靠整窗标量。

### 24.2 三类形状的定义（对应三件套）

| 形状 | 语义 | 未来路径特征 | 对应策略 |
|---|---|---|---|
| `quiet` | 无推进 | 全程低效率、无净位移、极值中位 | 箱体震荡逆势 |
| `advancing` | 推进中 | 高效率 + 低回吐 + **极值靠后** | 顺势 / 加仓 |
| `exhausted` | 收尾回吐 | **前半程已推进 + 后半程回吐** | 收紧移动止损 / 只持有 |

### 24.3 实测（XAUUSD M5，20167 样本，k=3，shape 空间）

| 簇 | 占比 | 效率 er | 回吐率 | 同向比 | 波动比 | 极差比 | 极值位置 | 破箱位置 | \|净位移\| |
|---|---|---|---|---|---|---|---|---|---|
| c1 → advancing | 22.5% | **0.439** | **0.160** | 0.639 | 1.236 | 1.547 | **0.980** | −0.101 | 1.912 |
| c0 → exhausted | **61.5%** | 0.224 | **0.626** | 0.558 | 0.879 | 0.816 | 0.523 | −0.525 | 0.678 |
| c2 → quiet | 16.0% | 0.366 | 0.573 | 0.583 | **2.740** | **3.165** | 0.584 | −0.436 | 1.009 |

**`advancing` 产出干净 ✓**：效率最高 0.439、回吐最低 0.160、**极值位置 0.980（极值几乎
就在窗口末端）**、同向比最高 —— 这是教科书式的"持续推进"路径。

**`exhausted` / `quiet` 没分出来 ✗**，原因是我自己的形状定义有缺陷：

> **整窗"回吐率"无法区分「趋势涨完回吐」与「从未推进的震荡」。**
> 因为纯噪声路径上 net≈0 而 mfe>0 → 回吐率天然趋近 1。证据就是 c0 占了 **61.5%**
> ——一个"衰竭"类不可能占六成；它实际是"低效 + 没守住"的大杂烩（|净位移| 仅 0.678，
> 却曾有 1.81 ATR 的有利偏移）。同时 c2 被判为 `quiet`，但它的波动比 2.740 / 极差比 3.165
> 是**最活跃的波动扩张簇**，命名与事实相反。

### 24.4 修正方案（下一步实施，一句话）

把**整窗回吐率**换成**两段式**形状描述：窗口切前后半程，分别计算

- `fwd_er_h1` / `fwd_er_h2`：前半程 / 后半程效率
- `fwd_rev_h2`：后半程净位移相对前半程的**反向幅度**（带符号，尺度无关）

于是三类可用**时间结构**判开（且全部尺度无关）：

| 形状 | 判据（形状语言，非绝对阈值） |
|---|---|
| `quiet` | 两段效率都低（前后都没推进） |
| `advancing` | 后半程效率 ≥ 前半程，且无反向 |
| `exhausted` | **前半程效率高 + 后半程净位移反向**（推进过、又吐回） |

关键区别：`exhausted` 要求"**曾经推进过**"（h1 高效），而 `quiet` 是"**一直没推进**"
（两段都低效）——这正是当前整窗口径丢掉的**时间信息**。

## 25. 实施：状态年龄（`age_bars`）—— 阶段的正确载体（2026-09-15）

### 25.1 结论先导（由三次失败推出）

| 尝试 | `init vs mid` 可学性 | 失败原因 |
|---|---|---|
| 4 类人工阈值标签 | AUC 0.535 | 定义重叠：69% 标签条件相同，判别项在**前视**路径上 |
| 4 类数据驱动聚类 | AUC 0.588 | 幅度不可预测（4.0 vs 1.3 ATR） |
| 3 类形状聚类（两段式） | 仍按幅度/波动分层 | 两段 `rev_h2` 是对称带符号量，簇均值互相抵消≈0 |

**三次同一结论**：「初生 / 中段 / 衰竭」**不是固定窗口内的形状属性**，而是"我们处在
更长趋势的哪一段"这一**跨窗口位置**属性 —— 任何单一固定窗口的签名都不含该信息。

**解法**：阶段改由 **状态年龄 = 纯过去可观测量** 承载，由状态机自己数出来，
既不需要预测，也不需要人工阈值。

### 25.2 实施内容

| 文件 | 变更 |
|---|---|
| `signal_tower/state_machine.py` | `FSMState.age_bars` / `FSMDecision.age_bars` 新增；`_to()` 迁移置 1；`_keep()` 保持 +1；`reset()` 归零；`same_bar_skip` 分支同步携带 |
| `signal_tower/scheduler.py` | 上屏 JSON 增加 `age_bars`（面板可观） |
| `tools/verify_state_machine_age.py` | **新增验证脚本**（`decide()` 是纯函数 → 可逐 bar 精确断言） |

**语义（已文档化并验证）**：
- 迁移 → `age = 1`（本根为第 1 根）
- 状态保持 → `age += 1`，**包括低置信跳过、单根推理失败**（那些 bar 上状态事实上仍在持续）
- 人工复位 / 震荡锁止 → 重新计数
- 一根 bar 只推进一次由 `step()` 的 `bar_time` 去重保证 → 年龄不会重复累加

### 25.3 验证结果：**23/23 通过**

覆盖：迁移需防抖、同态递增、低置信不打断、单根失败不打断、换态重置、
暂停优先、无持仓复位、震荡锁止、初始值。

### 25.4 ⚠ 验证中发现的一个真实设计交互（非实现缺陷）

`flat_reset_enabled=True`（默认）时，**「趋势态 + 无持仓」会在下一根立即复位 S0**
（`state_machine.py:213-216`，既有设计，防卡死）。其后果是：

> **`age_bars` 只在状态被"实质持有"时累积** —— 趋势态无持仓时年龄无从增长。

这与意图一致（年龄度量的是**交易的阶段**，不是空洞的状态），但策略层必须知道这一点：
**"轻仓试错（age 小）→ 顺势加仓（age 大）"的切换前提是已有持仓**，否则状态会被 flat_reset
直接清掉。验证脚本已把该交互写成显式注释与测试场景（`pos=1`），避免后人误改。

### 26.1 两条结论（一好一坏，均须如实记录）

→ "把状态定义从「阶段」改为「形状」"这个方向**得到支持**。

**坏：但仍未超过基线，且证据强度弱**：
1. **漏检 63.6%（35/55）** —— "更早"只在**自选的 20/55 命中子集**上成立，不是全面更早；
2. 误报 56.2% vs Donchian 9.9%；
3. **根因（2026-09-15 二次诊断，纠正上一条初判）**：

   | 分布 | quiet | advancing | exhausted |
   |---|---|---|---|
   | 训练段 | **5235（55%）** | 2846（30%） | 1431（15%） |
   | 样本外**真实** | 596（25%） | **1425（60%）** | 357（15%） |
   | 样本外**预测** | 504（21%） | **1786（75%）** | 88（3.7%） |

   样本外逐根准确率 **0.740**，对照"恒预测多数类" 0.599 → **模型确实带信息（+14.1pt）**。

   **⚠ 我上一轮"多类 argmax 存在严重类别偏置"的判断是错的，此处更正**：
   预测分布（75% advancing）与**真实分布（60%）只差约 15pt**，不是"几乎所有时间都在报警"的
   病理偏置。真正的原因是 **训练段与样本外段存在 regime 漂移**：
   **训练段以 quiet 为主（55%），样本外段以 advancing 为主（60%）**。
   而"检测器 = 非 quiet"这个定义在 advancing 占 60% 的段里**天然大部分时间处于 ON**，
   上升沿自然对不上切换点 → 漏检 60% 是**评测口径造成的**，不是模型失效。

   **由此得到两条工程结论**：
   1. 形状模型的正确评价指标是**状态描述准确率**（0.740 vs 0.599），**不是"触发器漏检率"**
      —— 它本来就是描述器，不该被拿去当触发器打分；
   2. 该验收门的结果**强依赖评测段 regime**（本段 trend 占比 60%）。后续必须
      **滚动多段评估**，否则结论会被单一段落的 regime 左右。

   （另注：`exhausted` 召回仅 24.7%（88/357）—— "收尾回吐"仍是三类里最难的一类，
   与 §24.3、§25 的判断一致。）

## 28. 可探测提前量上限：**不是口径所限，是链路没问对问题**（2026-09-15）

背景（§27.4）：多折实测所有检测器中位提前量都在 ±1 bar 内 → 只做到"同步"。
须先分清：是**信息不存在**（口径所限，调模型无用），还是**模型没学到**（有提升空间）。

工具：`tools/eval_anticipation_bound.py`（新增）。方法（非循环）：
在每根 bar 上，**只用 k 及以前的特征**预测「未来 (k, k+L] 内是否出现一次趋势起点」，
取 `gt=False` 的样本（即"当前不在趋势，预测即将发生"），时序 OOF 测 AUC 随 L 的衰减。

### 28.1 实测（XAUUSD M5，样本 11890，趋势起点 1040 次）

| L (bar) | 可用样本 | 正例率 | **AUC** | ΔAUC | 判读 |
|---|---|---|---|---|---|
| 1 | 4020 | 21.3% | **0.7078** | +0.208 | 信息存在 ✓ |
| 2 | 4020 | 34.4% | **0.7379** | +0.238 | 信息存在 ✓ |
| 3 | 4020 | 43.5% | **0.7459** | +0.246 | 信息存在 ✓ |
| **5** | 4020 | 56.2% | **0.7599** | **+0.260** | 信息存在 ✓（最强） |
| 8 | 4020 | 68.3% | **0.7428** | +0.243 | 信息存在 ✓ |
| 12 | 4015 | 78.2% | **0.7424** | +0.242 | 信息存在 ✓ |
| 20 | 4015 | 89.2% | 0.6436 | +0.144 | 信息存在 ✓ |
| 30 | 3212 | 95.6% | **0.5455** | +0.046 | **≈不可探测 ✗** |

### 28.2 结论

> **可探测提前量上限 ≈ 20 bar**（L ≤ 20 全部 AUC > 0.64；L=30 衰减到 0.545）。
> 而在 L=1~12 区间 AUC 稳定在 **0.71~0.76**，**L=5 达峰 0.7599**。

**⇒ 不是标签口径所限，是模型/链路不足。** 未来 5~12 根内的趋势起点**是可预测的**
（AUC 0.74~0.76），而当前检测器只做到 **0 bar**。差距来自**训练目标**：
现有链路从未把「预测起点」当作显式任务，而是从 4 类 argmax + 防抖间接推导 ——
`trend_init` 又恰是实测最不可分的一类（§22）。**问错了问题，自然得不到答案。**

### 28.3 由此确定的核心修正（下一轮实施）

> **把「预测起点」做成显式二值任务，替代从 4 类 argmax 推导触发器。**

| 件 | 新承担者 | 依据 |
|---|---|---|
| **触发器** | **显式"起点预测"模型**：目标 = 未来 L\* 根内出现趋势起点（L\*=5，AUC 峰值；可做成多 horizon 或生存分析式） | §28.1：L=5 AUC **0.7599** |
| 状态描述 | 形状模型（数据驱动簇） | §26.1 更正后：准确率稳定高多数类 10~30pt |
| 方向 | `trend_direction` 规则模块 | §20 |
| 阶段 | `age_bars` | §25（23/23 验证） |

### 28.4 两点必要的严谨性标注

1. **跨 L 的 AUC 不可直接比较**：正例率随 L 从 21% 升到 96%，base rate 变化本身会影响 AUC。
   稳健读法是「**每个 L ≤ 20 都 > 0.64**」这一事实，而非"AUC 随 L 上升"这一趋势。
   下一步应改用**固定 base rate 的指标**（如 precision@k 或负例下采样后 AUC）复核。
2. **该上限相对本特征集**（27 维、单周期、无成交量/盘口/多周期）。加入此类特征可抬高上限，
   故 20 bar 是**当前信息集下的**上限，不是市场的物理上限。

### 29.3 关键诊断：定位能力**存在**（我最初的判断有误，此处更正）

先纠正一个错误：我一度推断"模型只有全局排序能力、没有事件定位能力"。加入定位诊断后
（`P(onset)` 按"距最近起点的距离 d"分组）**该推断被数据否决**：

| d (bar) | 1 | 2 | 3 | 5 | 8 | 12 | 20 | 全体 |
|---|---|---|---|---|---|---|---|---|
| 平均 P(onset) | **0.847** | 0.803 | 0.752 | 0.676 | 0.554 | 0.564 | **0.483** | 0.666 |

### 29.4 触发器失效的真正机制（有数据支撑）

既然定位能力存在，为何按水平过阈仍然失败？因为：

> **`P(onset)` 是在起点前若干根"逐步抬高"的（d=5 已 0.676、d=3 已 0.752），
> 而不是只在起点那一根跳高。** 于是"P 高于阈值"这个状态会**横跨多个事件持续有效**，
> 触发器一旦 ON 就长时间不灭 → **一根 ON 段覆盖多次起点**，其"上升沿"自然对不上
> 单个起点 ⇒ 表现为**高漏检 + 中位滞后**（§29.2 两张表完全一致）。

**⇒ 正确形态：用 P 的"动态"（上升速率 / 局部峰值）做触发，而不是用它的"水平"。**

### 29.5 下一步（L1g）

实现**动态触发器**：以 `ΔP`（如 P[t] − P[t−m] 或 P 的局部极大）作为触发条件，
取代 `P ≥ 阈值`；候选形式：
1. `P` 自低位快速抬升（跨越其自身滚动分位）；
2. `P` 出现局部峰值（`P[t] > P[t±w]`）且峰值 ≥ 滚动分位；
3. 以上任一 + 方向确认（`trend_direction` 非 NONE）。

验收仍用同一多折门，指标 = **中位提前量 + 漏检 + 误报**三者同时看。
**这是把"信息可定位"（§29.3）转化为"可用触发器"的最后一环。**

## 30. 动态触发器 + 组合触发器：**触发器问题基本解决**（2026-09-15）

### 30.1 动态触发器（用 P 的动态替代水平）

按 §29.4 的机制结论实施两种动态形式（`eval_state_leadtime.py`）：
- `onset_rise`：`ΔP = P[t] − P[t−m]` ≥ 训练段 OOF ΔP 的 (1−触发率) 分位
- `onset_peak`：`P[t]` 为 ±w 邻域最大 且 ≥ 训练段 P 的 (1−触发率) 分位

**多折实测（3 折汇总，262 次真值切换）：**

→ **水平 → 动态：漏检 142 → 54、误报 18.8% → 9.6%**，且 `onset_rise` 是**唯一三折中位全为负**

## 33. ⚠ 时间对齐 bug 及三处结论更正（2026-09-15，L3b 过程中发现）

### 33.1 Bug 本体

工具脚本普遍使用 `pd.to_datetime(col, utc=True).astype("int64") // 1_000_000_000`
把时间列换算成 Unix 秒。**该写法隐含假设 dtype 是纳秒**，但 pandas 2.x 的 `to_datetime`
对**字符串列**返回 `datetime64[us]`（微秒）→ `//1e9` 得到的是"**千秒**"，
把 5 分钟 bar 塌缩（实测：形状表 20168 行只剩 **6071** 个唯一键）。

**最危险之处**：若比较的两侧都用同一公式，则 `k_ep[pos] == ep` **仍然恒真**
（连"未匹配=0"的自检也会通过）—— 于是按 bar 对齐的指标（ADX / 斜率 / 突破）
**静默取错行**，M5 上最多偏 3 根，H1 上最多偏近 1 根。

**修复**：新增 `build_state_labels.epoch_s()` 作为**全仓唯一实现**，
按 `dtype.unit`（tz-aware 用 `.unit`，朴素用 `np.datetime_data`）换算，不假设单位；
并处理 `.astype("datetime64[ns]")` 对 tz-aware 会抛 TypeError 的问题。
三个脚本（`eval_state_leadtime` / `eval_trend_direction` / `validate_shape_semantics`）
一律委托调用。

## 36. 【P0 数据质量】高周期数据不自洽的根因：K 线 `high/low` 伪极值（2026-09-15）

### 36.1 触发本次调查的现象

用户选择"先查清并治理高周期数据不自洽"。起点是 L5 补 M15 时，跨周期一致性无法成立：

### 36.2 根因（已用断崖式证据锁定）

**写入端 upsert 语义有害**：`high = GREATEST(existing, new)`、`low = LEAST(existing, new)`
是**单调累积**——一次坏写入（陈旧/异常行情快照）把伪极值**永久锁死**在该 bar 上，
此后所有正常写入都无法纠正；同时 `open` 从不更新、唯 `close` 被覆盖
⇒ 形成**"close 全对、open/high/low 全错"**的特征签名。

**判据复现（XAUUSD M5，2026-08-14 17:00~17:35 同时段对照）**：

| M5（每 5 分钟 bar） | open | high | low | close | range |
|---|---|---|---|---|---|
| 17:00 | 4381.43 | 4401.97 | **4322.77** | 4383.37 | **79** |
| 17:05 | 4386.81 | 4398.07 | **4322.82** | 4382.25 | **75** |

| M30（覆盖同样 30 分钟） | open | high | low | close | range | 衔接 gap |
|---|---|---|---|---|---|---|
| 17:00 | 4385.89 | 4386.44 | 4379.28 | 4379.53 | 7 | **0.01** |
| 17:30 | 4379.47 | 4382.78 | 4376.31 | 4378.46 | 6 | **−0.06** |

M5 单根 5 分钟 range 达 71~79 点，而覆盖它 6 倍的 M30 仅 6~7 点（M1 单分钟 range 中位
仅 1.76）→ **M5 的 high/low 被放大一个数量级**；且 `low` 被**钉在同一值连续 8 根**
（真实行情不可能）。同时**真实 M30 衔接 gap≈0.00**，而 M5 有 **31.08%** 相邻 bar
`|open − prev_close| > 1`、最大 **1464.34**。**`close` 链完全正确且与真实 M30 的 close
逐根相等** ⇒ `close` 可信，`high/low/open` 被污染。

### 43.3 (b)(c)(d)：结论与**刻意停手**的理由

#### (b) 桥接受并下单 —— 追清后的结论：**桥侧无需改；但风控引擎必须改一处（已改）**

实测：桥消费的是 **`signal:risk_passed`**（风控**之后**），且 `mt5_bridge.py` 内
**没有 `signal_mode` 白名单**（唯一 mode 特例是 `manual_mirror` 的手动镜像护栏）。
⇒ **桥侧"接受"无需改动**（magic 61/62 由塔设置、桥透传）。

**追清风控引擎（`hcm-risk-engine/risk_engine/stream_consumer.py`）后有两个结论：**

| # | 结论 | 影响 |
|---|---|---|
| 1 | **不会因未知 mode 丢弃信号**：全仓库仅 `manual_mirror` 有 mode 特例；未知 mode 走正常规则链并被透传到 `risk_passed`（`:549` 透传 `signal_mode`） | ✅ 原未知点解除 |
| 2 | ⚠ **会无条件重算并覆盖 `lot`**（`:179-186` `signal_data["lot"] = new_lot`），按 `confidence` 分档 | **FSM 手数语义被破坏（见下）** |

**结论 2 的机理（重要）**：`_apply_dynamic_lot` 的 `confidence` 口径是**评分引擎的 0–100 制**
（`:136-141` 仅在 `score > 1.0` 时归一化）；而 FSM 信号传的是**模型决策边际**
（top1−top2，典型 0.1~0.4）→ **≤1.0 不归一化** → 被当"低置信" → 落最小档 `mult_low`(0.5)

> ⇒ FSM 单手数**恒为 `base × 0.5`**，规格的**震荡梯度手数（0.5/1.0/1.5/2.0）与趋势 base_lot
> 全部失效**。用 `ai_lot_tier` 也救不了（风控只有 low/mid/high **3 档**，表达不了 S1 的 4 档）。

**已修**：与 `manual_mirror` 同款处理 —— `signal_mode` 以 `state` 开头时**直接 return，
不动 `lot`**。手数由塔的 `_fsm.lot_multiplier` 表达、由**桥**按 `base × lot_multiplier` 落地。
**`inert` 保证**：当前生产无任何 `state*` 信号 ⇒ 不影响既有 hexp/scoring/live_override。

⚠ **手数落地链的完整契约（桥实现时必须照做，否则梯度仍失效）**：

```
塔：lot=0 + _fsm.lot_multiplier（S1 梯度 / 趋势=1.0）

 → 桥：lot<=0 时用自身 base，并乘 _fsm.lot_multiplier  ← **尚未实现**
```

⇒ **在桥实现这一乘算之前，绝不可启用 FSM 下单**（否则 S1 梯度与趋势手数全部失真）。

### 43.4 ✅ (e) 移动止损 clamp 规则（本次定案，供 (c) 实现）

规格字面"近 N 根低/高 ∓ ATR×k"会产生**无效止损**：回踩入场（仅 0.5×ATR）时
`[近N根高] − k×ATR` 可能**高于入场价** → 多头 SL 在市价上方，MT5 会拒绝
（整链回放实测：该口径把均值 R 从 +0.059 抬到 +0.407、胜率从 40% 抬到 84.6%，**20 倍虚增**）。

**定案规则（三步，缺一不可）**：

1. **候选值**：`cand = extreme(近 N 根) ∓ k×ATR×trail_mult`（N=`state.trend.trail_lookback`）
2. **不许越过市价**：多头 `sl = min(cand, bid − min_dist)`；空头 `sl = max(cand, ask + min_dist)`；
   其中 `min_dist = max(state.trend.min_sl_atr × ATR, 经纪商 stops_level × point)`
   —— 前者防"贴脸止损"被噪音扫掉，后者防 MT5 `Invalid stops` 拒单。
3. **只前移不放宽**：多头只允许 `sl` 增大、空头只允许减小（与规格"只前移"一致）。

新增配置键：`state.trend.min_sl_atr`（建议初值 0.3，⚠ 未标定）。

## 44. FSM 参数链定案：手数取风控基础手数，SL/TP 链动时段系数（2026-09-15）

用户提问确认：**S1 梯度（0.5/1.0/1.5/2.0）与趋势 base_lot 是否取风控配置的基础手数？
SL/TP、保本、移动止盈是否链动 `close.<时段>.*`？** → **是**，本节把该链**固化并逐段验证**。

### 44.1 完整参数链（已实现 + 已验证）

```
基础手数 base ── 风控配置（**唯一真源，在风控引擎内解析**）
   · symbol.{品种}.tower.lot_size（若 ≤ risk.max_lot_per_trade）
   · 否则 risk.lot_base
   · 封顶 risk.max_lot_per_trade
        ↓  × FSM 倍率（塔给出，顶层流字段 fsm_lot_multiplier）
   S1 箱体单 = base × ladder[连续止损档]（0.5/1.0/1.5/2.0）
   趋势单   = base × 1.0（S2/S3；S3 加仓同为 base，规格 10.2）
        ↓  lot 由**风控**算好，桥与其它 mode 一样直接用

SL / TP / 保本 / 移动止盈 ── 桥按 **close.<时段>.* 时段系数** 计算（塔不写死数值）
   · 开仓 SL      : close.<session>.trailing_stop_distance × ATR（`sl_locked` 可豁免）
   · 开仓 TP      : close.<session>.tp_atr_multiplier × ATR
                    ← **例外**：S1 传 `tp1 = 冻结箱体中值`（非 0 → 桥直接采用）
   · 保本         : close.<session>.breakeven_atr_mult / breakeven_tp_ratio
   · 移动追利     : close.<session>.trail_start_atr_mult / trail_wide_atr_mult / tp_relay_enabled
   · **FSM 增量**  : `fsm_trail_mult`（S4 收紧，<1.0）、`fsm_exit_ready`（准备离场）、
                    `fsm_trail_lookback`（"近 N 根极值"的 N）
```

**为什么手数在风控算而不是在桥算**：`base` 的解析代码本来就在风控引擎里
（`_apply_dynamic_lot`）。让桥再解析一次就是**第二份 base 真源**（本仓库红线）。
故 FSM 倍率随信号上传、由**持有 base 的那一方**乘算 —— 桥只需用 `lot`，与所有其它 mode 一致。

### 44.2 跨组件字段（顶层流字段，不是塞进 JSON）

FSM 需要被下游消费的字段一律为**顶层流字段**（与 `ai_sl_mult` / `sl_locked` /
`zone_tp_level` 同一约定）：

| 字段 | 消费方 |
|---|---|
| `fsm_state` / `fsm_lot_multiplier` | 风控（算 lot） |
| `fsm_trail_mult` / `fsm_exit_ready` / `fsm_trail_lookback` | 桥（FSM 移动止损分支） |

⚠ **为什么不塞进 `indicator_values`**：它到下游是 **JSON 字符串**
（`shared/redis_client.py:146` 对 dict/list 做 `json.dumps`），风控与桥都得先 `json.loads`。
⚠ **新增流字段必须同步加进风控 `_publish_risk_passed` 白名单** —— 该处已有前车之鉴注释：
`zone_level` 等曾漏传 → 桥侧取 0 → "出信号不下单"。

### 44.3 验证：`verify_fsm_param_chain.py` **21 项全过**

### 49.7 ⚠ 过程记录：一次由工具链造成的文件损坏（**务必记住**）


**结果把整个迁移文件变成乱码**（`鐡掑濞嶆＃鏍偧…`）—— PowerShell 5.1 的 `Get-Content`

2. **绝不用 `Get-Content` 做 UTF-8 文本的读-改-写**（要读就用 `-Encoding UTF8`，

### 56.5 一个流程教训（影响所有配置类改动）

**写 PG 迁移不足够**：`ConfigProviderV3` 解析顺序是 L1(内存 30s) → **L2(Redis

必须再 `HSET hcm:config:v2 <key> <val>` + `PUBLISH hcm:config:invalidate <key>`。
规范做法是用 `ConfigProviderV3.set()`（PG → Redis → PUBLISH）。**0036/0037/0038 的注释里
都已写明这一步**，后续所有配置迁移必须照此执行。
