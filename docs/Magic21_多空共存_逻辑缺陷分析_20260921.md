# Magic=21 多空共存 —— 下单逻辑与缺陷深度分析

- 日期：2026-09-21（事件发生于 2026-09-21 06:31–06:34 UTC / 14:31–14:34 CST）
- 性质：**只读审计**，未改动任何生产数据 / 配置 / 进程
- 结论强度：现象与代码路径=**硬证据**；MT5 账户对冲模式=**高置信推断**（见 §9）

## 0. TL;DR

**Magic=21 = `live_override`（bar 内实时触发）**。多空同存**不是"跨 magic 族设计"，而是同一账户、同一 magic=21 下 BUY 与 SELL 同时挂单、且谁都没被平掉**。

根因是一条**贯穿全链路的"同向盲区"**：
1. **信号塔**：TREND 下"反向"有独立冷却 `trend_reverse_cooldown_seconds`（默认仅 **90s**），反转信号 90s 后即可再发，且**不要求先平掉反向持仓**。
2. **AI 闸门**：当前 `real_ai_mode=decoupled`，AI 裁决以 `observed_only / counterfactual` 记录，**不可拦单**（本单 AI 甚至给出 DOWNGRADE B→C，仍 `passed=True`）。
3. **风控引擎**：8 条规则**没有任何一条检查"反向持仓"**。限仓只数**同向**（"反向持仓不再挤占额度" 属 2026-08-13 刻意改动）；保本冷却只按 (账户, 方向, magic 族)；接刀护栏仅当 `reverse_order=True` 才跑（本单未跑）。
4. **全代码库 `hedge / netting / 锁仓 / close_opposite / 反向平仓` 匹配数 = 0** —— **没有任何机制负责平掉反向单**。
5. MT5 账户为**对冲(hedging)**模式 → 反向单不会净额轧平，于是"两个独立开仓"直接变成**锁仓**。

一句话：**所有闸门都按"方向"隔离思考，而"平掉反向"这件事谁都不负责。**

## 2. Magic=21 是什么 + 完整下单链路

`shared/magic_family.py:20-26`

```python
MAGIC_FAMILY_HEXP          = 11   # hexp 乘幂引擎 M5 bar 收盘主信号
MAGIC_FAMILY_SCORING       = 12   # 默认评分引擎
MAGIC_FAMILY_LIVE_OVERRIDE = 21   # bar 内实时触发   ← 本次主角
MAGIC_FAMILY_RANGE         = 55   # RANGE 均值回归
MAGIC_FAMILY_STATE_OSC     = 61   # FSM S1 箱体逆势单
MAGIC_FAMILY_STATE_TREND   = 62   # FSM S2/S3/S4 顺势单
```

**Magic=21 = live_override（"救援"信号）**：`scheduler.py:1437 _live_override_loop` 每 **5s** 轮询，实时 ADX 持续 ≥floor 达 `sustained_sec`(默认30s) 且距上次 `rate_limit_sec`(默认60s) 即调用 `_produce_signal(live_override=True)`（`scheduler.py:1504`）；另有 `_live_score_publisher` 每 3s 触发（`scheduler.py:3936`）。→ **它是唯一"bar 内可反复重算方向"的高频入口**，方向随指标漂移而翻。

完整链路：

```
signal_tower._produce_signal(live_override=True)
  ├─ Step6 冷却  : compute_cooldown(regime, pre_score, direction, state.last_direction, ...)
  │                 TREND 且 direction != last_direction → base = trend_reverse_cooldown_seconds
  ├─ value gate  : ai.lm.value_gate_enabled（默认 False → 不生效）
  └─ 发布到 signal:stream（signal_mode=live_override, magic=21）
        ↓
risk_engine.stream_consumer → RuleChain.evaluate()
  Rule1 min_confidence → Rule2 max_single_lot → Rule3 max_total_lot
  → Rule4 max_open_positions(仅同向) → Rule5 daily_loss → Rule6 margin
  → Rule8 cooldown(同向保本闸门) → [Rule9 reverse_order 仅当 reverse_order=True]
        ↓
dispatcher → gateway(tcp_bridge) → MT5 EA 下单（对冲账户：直接开新仓，不平反向）
```

## 3. 逐层根因（全部附 file:line）

### 根因 A｜信号塔：反向冷却仅 90s，且不要求平反向
`hcm-signal-tower/signal_tower/scoring_engine.py`
- `:1661-1662`：`elif not same_dir: base = self._trend_reverse_cool`
- `:1858`：`self._trend_reverse_cool = await self._config.get_int("trend_reverse_cooldown_seconds", 90)`
→ **反转冷却默认 90s**。BUY(06:31:27) → SELL(06:34:42) 间隔 **195s > 90s**，冷却满足即放行。塔内**没有任何"存在反向持仓"的检查**。

### 根因 B｜AI 闸门：decoupled 下仅观测，无否决权
- `hcm_ai.gate_decision` 元数据 `real_ai_mode=decoupled, observed_only=True, counterfactual=True`，`action=DOWNGRADE` 但 `passed=True`。
→ 与已知生产事实一致（`ai.mode=decoupled`）。**AI 无法阻止反向开仓**。

### 根因 C｜风控 Rule4 限仓"只数同向"（刻意的 2026-08-13 改动）
`hcm-risk-engine/risk_engine/rule_chain.py`
- `:463-467`：
  ```
  # 【2026-08-13 修复】按「同向实时持仓数」判定：仅统计与信号同方向的 open 持仓，
  # 反向持仓不再挤占额度。
  direction = str(signal_data.get("direction","")).upper()
  ```
- `:472`：`open_count = await self._get_open_positions_count(account_id, symbol, direction)`（`direction` 传入为**同向**过滤）
- `:496`：`passed = open_count < threshold`
- `:1016-1018`：SQL `... AND direction=$n`（同向）

→ BUY 已开时，SELL 的同向计数 = **0** < 阈值(max_pos=5) → **PASS**。反向 BUY 对限仓**完全不可见**。
→ **副作用**：`max_pos=5` 实际是**每方向 5 笔**上限 → 单账户单品种理论可同存 5 BUY + 5 SELL = **10 笔**。

### 根因 D｜风控 Rule8 保本冷却按 (账户, 方向, magic 族)
- `:605-608`：`_fam = _magic_family(signal_data.get("magic"))`；判定维度 = (账户, 方向, magic 族)
- `:721-733`：`SELECT ... FROM hcm_trading.positions WHERE account_id=$1 AND direction=$2 ...`
- `:756-764`：`if entry is None: → passed=True`（"无同族 open 持仓 → 放行"）

→ SELL 查询"同向同族 SELL 持仓" → 无 → **放行**。反向 BUY 不可见。

### 根因 E｜风控 Rule9 接刀护栏是**条件规则**，本单未触发
- `:322-333`：`_rro = _as_bool(signal_data.get("reverse_order", False))`；**只有 `True` 才跑** `_check_reverse_order`
- `:842-943`：护栏内部"是否首单"由 `_account_be_from_db(account_id, direction, ...)`（`:816-817` `WHERE account_id=$1 AND direction=$2`）判定

→ 本单 `reverse_order` 非 True（日志 `reverse_order` 0 命中）→ **护栏整段跳过**；即便触发，其 BE 判定同样**只看同向**。双重同向盲区。

### 根因 F｜全链路无人负责"平反向"（0 匹配 = 最强证据）
全仓 `*.py` 检索 `hedge|netting|锁仓|对锁|close_opposite|反向平仓|平掉反向|close_reverse` → **No matches found**。
- 塔侧唯一的"反向"概念 `hexp.reverse_order` 是**翻转信号自身方向**（策略级接刀），**不是**平掉反向持仓（详见 `docs/signal_tower_reverse_order_audit_20260906.md`）。
- 桥/网关仅做 `BUY→ORDER_TYPE_BUY / SELL→ORDER_TYPE_SELL` 直译（无"先平后开"）。
→ **系统从来没有"反转=平旧开新"的语义，只有"再开一笔"。**

### 根因 G｜环境放大：MT5 对冲账户
对冲账户下反向单不被净额轧平 → 根因 A–F 的"盲目开单"直接落地为**锁仓**。（净额账户会轧平，问题会以另一种形式暴露。）**高置信推断**，见 §9。

## 5. 影响与风险

| 项 | 说明 |
|---|---|
| **直接成本** | 锁仓双向点差 + 隔夜掉期（swap）双付；占用双倍保证金 |
| **净敞口≠0 的隐性暴露** | 两腿手数/lot 相同 ≠ 完全对冲：点差、滑点、swap、以及 SL/TP 触发时序差，都会产生**非预期净盈亏** |
| **风险预算被稀释** | 限仓实际为"每方向 max_pos=5" → 真实总敞口是最初设计意图的 **2 倍** |
| **震荡市放大** | 行情来回穿越镜像价位时会**先打一侧 SL 再打另一侧**，两腿先后止损（whipsaw 双亏） |
| **手工处置困难** | 15 分钟内可累积多对锁单，人工拆解成本高；平错腿会瞬时变成单向裸敞口 |
| **观测污染** | `gate_decision` 以 `cfg_override=coupled` + `counterfactual` 存反事实裁决，易被误读为"AI 已放行" |

## 6. 附带发现（同批审计，均为硬证据）

1. **`scheduler.py:2056` 注释错误**：称"`hcm_trading.positions` **没有 `magic` 列**"。实测该表**有** `magic bigint`（且 `rule_chain.py:722` 正在 select 它）。→ 该注释所述前提为假，据此搭建的 FSM 在仓识别（`:2043-2078`）用的是替代启发式，**精度可疑**，建议复核。
2. **`orders` 表僵尸行**：`rule_chain.py:700-708` 自述 `position_sync.py` 平仓时 **INSERT `order_status=2` 新行**而非 UPDATE → `order_status=1` 的开仓行 `close_time` 永为 NULL（累积 ~492 条）。→ **"当前未平持仓"不能用 orders 表判断**，唯一可靠真值源是 `positions`。
3. **Rule8 DB 故障 fail-open**：`rule_chain.py:742-754` DB 异常 → `passed=True`（自述"已拍板"），风险闸门在 DB 故障时降级放行。
4. **配置键缺失 → 跑代码默认值**：Redis 无 `hcm:config:risk*` 任何键；实跑默认 `max_pos=5, cool_min=5, score_pos_enabled=False`。→ 面板/库里的"配置"可能并未生效（配置≠生效，与本项目历史缺陷同类）。
5. **`signal_status` 语义未文档化**：实测 `0=filtered`、`3=成交`；`1/2` 语义在本次分析中未能从日志确证（§9）。

## 7. 修复方向（选项，本轮**未实施**，待授权）

> 按用户「AI 仅持否决/降级权」与「反转应平旧」的既有口径，下面按"改动面从小到大"排列：

**方案 1（最小、塔侧）— 反转即先平**
在 `_produce_signal` 判定 `direction != state.last_direction` 且该 symbol 存在反向持仓时：先发 `signal_dir=CLOSE`（指向反向持仓的 ticket）再发新单；或直接把新单标记为 `is_reverse=true`。

**方案 2（风控侧）— 新增"反向敞口"规则**
在 `rule_chain.evaluate()` 增加 Rule：若 (账户, 品种) 已存在**反向** open 持仓，则 **拒绝新反向开仓**（或按配置允许"平旧开新"）。这是把"同向盲区"补上的最小侵入点，且不依赖塔是否发 CLOSE。
- 需同时决定：**拒单** 还是 **先平后开**；以及是否按 magic 族豁免（例如 HEXP(11) 与 FSM(62) 分属不同策略意图，是否允许互相对冲）。

**方案 3（塔侧冷却）— 反向冷却与"存在反向持仓"联动**
`trend_reverse_cooldown_seconds`(默认90s) 过短；可改为"存在反向持仓时禁止反向开仓，直到反向持仓归零"。

**方案 4（观测面）— 审计口径修正**
- `gate_decision` 的 `counterfactual/observed_only` 与真实裁决分离，避免误读。
- 修正 `scheduler.py:2056` 假前提注释，并把 FSM 在仓识别改为按 `positions.magic` 真值过滤。

**无论选哪个，都必须先明确一条策略问题**：**同一品种同方向是否只允许一个策略族持有？跨族（如 61 逆势 / 62 顺势 / 11 主信号）是否承认有意对冲？** 当前 `magic_family` 的设计（"不同族互不牵连"）在**方向维度上留了同样的洞**，需要一并拍板。
