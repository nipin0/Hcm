# Magic=11 / 21 频繁下单 · 下单逻辑链路缺陷分析

> 生成日期：2026-09-21
> 关联文档：`Magic21_多空共存_逻辑缺陷分析_20260921.md`（前序，聚焦 21 的多空同存）
> 范围：只读源码审计 + 生产 PG / 持仓实证。**未改动任何生产代码/配置**（红线：写操作需显式授权）。

## 0. 结论速览（先讲结论）

1. **两个 magic 都确实在"频繁下单"，且有硬证据**：近 7 天生产信号 HEXP(=11) 146 条、live_override(=21) 134 条；活跃交易日各自 20–39 条/天。当前**在仓**持仓 magic=11 共 42 单、magic=21 共 58 单（合计 100 单），且**两族都在同时持有 BUY 与 SELL**。
2. **"频繁"的成因两族不同**：
   - **Magic=21（live_override）是真正"棒内/日内高频"**：它**绕过了 per-bar 幂等闸门**（`scheduler.py:2840`），唯一节流是 30s 限流 + 边沿触发；而**边沿在"阈值抖动 / 方向翻转"时会反复重新武装**（`scheduler.py:1737、1740`），导致震荡/毛刺行情里每 30s 再触发一次、 whipshaw 里 BUY/SELL 交替触发。
   - **Magic=11（HEXP）本身是 per-bar 1 单**（幂等闸门生效），它的"频繁"来自 **① 每根 M5 bar 都可能在条件满足时出单（自然节奏）+ ② 信号被 copy-trading 扇出到多账户（信号源账户=6，持仓落在 6 与 9）+ ③ 持仓只增不减（无反向平仓）→ 累计 42 在仓**。HEXP 不是棒内 spam，是"持续叠单"。
3. **两族共享同一致命下游缺陷**：**全代码库无任何"平反向/锁仓/netting"逻辑**（grep `hedge|netting|锁仓|close_opposite|反向平仓` = 0 命中），且风控规则**全部"同向盲区"**（Rule4 只数同向持仓、Rule8 冷却按 (账户,方向,族) 计数、Rule9 接刀护栏仅在 `reverse_order=True` 才跑）。→ BUY 与 SELL 可同账户同族并存并累加，最终堆到 100 在仓。

## 2. Magic=21（live_override）"频繁"根因 —— 棒内高频

### 2.1 触发源：`_live_score_publisher`（每 3s 轮询）
`scheduler.py:1576` 起，C 层护栏：方向稳定 ≥2 周期(6s) + 限流 ≥30s + **单棒单发** + 边沿触发。

### 2.2 缺陷 A：per-bar 幂等闸门被绕过（核心放大因子）
`scheduler.py:2840`
```python
if not (live_override or value_drive):
    ... # 同 bar 去重：last_produced == current_bar_open → return
```
→ **HEXP 走此分支，受 1 单/棒 约束；live_override 直接跳过该分支，无任何 per-bar 上限**。其唯一节流只剩 30s 限流。

### 2.3 缺陷 B：边沿在"阈值抖动 / 方向翻转"时反复重新武装
`scheduler.py:1731-1742`
```python
if score_result.direction in ("BUY","SELL"):
    if score_result.direction == stable_dir:
        stable_count += 1
    else:
        stable_dir, stable_count = score_result.direction, 1
        state.live_edge_armed = True          # 方向翻转 → 重新武装
    if not score_result.threshold_passed:
        state.live_edge_armed = True          # 分值回落门槛下 → 重新武装
```
机制：
- 震荡/近门槛行情：pre_score 在阈值上下抖动 → 每次回落都 `live_edge_armed=True` → 30s 限流一过即再触发 → **每 30s 一单**。
- whipshaw：BUY→SELL→BUY 翻转 → 每次翻转重新武装 → 双向交替触发 → **BUY 与 SELL 都开**。
- 触发后 `:1762-1763` 才 `live_edge_armed=False` 且 `last_live_trigger_bar=_cur_bar`，即"同一事件一单"只在**分值持续在阈上且不翻转**时成立；一旦抖动/翻转即失效。

### 2.4 缺陷 C：单棒单发守卫的实现脆弱性（风险，需确认）
`scheduler.py:1743`
```python
elif _cur_bar is not None and state.last_live_trigger_bar == _cur_bar:
    pass  # 同一根 K 线已触发过，单棒单发
_cur_bar = klines[-1].get("open_time")   # :1696
```
守卫**依赖 `klines[-1]` 存在 `"open_time"` 键**。若该键名不符（如 `"time"`）或缺省 → `_cur_bar=None` → 该分支 `is not None` 为假 → **单棒单发静默失效**，叠加缺陷 B 可在单棒内多次触发。建议核实 `klines` 结构键名；但即便键名正确，缺陷 A/B 已足以解释高频。

### 2.5 Step6 冷却对 21 几乎无约束
`scoring_engine.py:1656-1662`：TREND 同向且 pre_score>_trend_bypass_score → `base=0`（无冷却）。live_override 在持续同向趋势里冷却=0，仅赖 30s 限流。

## 3. Magic=11（HEXP）"频繁"根因 —— 持续叠单 + 扇出 + 只增不减

### 3.1 HEXP 本身是 per-bar 1 单（幂等闸门生效）
HEXP 由 `_symbol_loop` 在 bar 收盘时调用 `_produce_signal(state)`（`scheduler.py:1332`），受 §2.2 幂等闸门约束 → **至多 1 单/棒**。故 HEXP 不是棒内 spam，是"每棒可能 1 单"的自然节奏（25–36 单/天）。

### 3.2 放大因子 1：copy-trading 扇出
信号源账户仅 6（§1.3），但 magic=11/21 持仓落在 **6 与 9** → 1 条信号被复制到 ≥2 个账户，下单量 ×N。`order_executor.py:141` 还会对复制账户重设 `magic = DEFAULT_MAGIC_PREFIX + (account_id%1000)`（FSM 族 magic 如 61010100/62021101 即此产物）；**账户 9 上仍见原始 magic 11/21**，说明 9 要么也跑 signal-tower，要么该复制路径保留了原 magic —— 这点需结合 copy-trading 配置进一步确认，**不臆断**。

### 3.3 放大因子 2：持仓只增不减（共享下游缺陷，见 §4）
HEXP 每棒出的单不被反向平仓、不被同族同向上限有效拦停 → 持续累加，最终 42 在仓。

### 3.4 HEXP 自身"保守偏放过"历史
`hexp_engine.py` 经 2026-08-13 修复极值闸门后恢复 active_model=hexp，但引擎仍偏保守（拦截率待观察）；HEXP 单量受 regime/cooldown 节流，天然低于 live_override。

## 4. 两族共享的致命下游缺陷：无反向平仓 + 同向盲区

（前序 `Magic21_多空共存` 文档已详述，此处汇总）

- **全代码库 0 条平反向逻辑**：grep `hedge|netting|锁仓|close_opposite|反向平仓` = 0 命中。MT5 对冲账户下，反向单不自动净额 → 锁仓/双向同存。
- **风控 Rule4 `_check_open_positions`**（`rule_chain.py:463-472`）：持仓数上限**只计同向**（2026-08-13 刻意改为"反向不挤占额度"）→ 反向可无限叠。
- **Rule8 `_check_cooldown`**（`rule_chain.py:565-833`）：冷却键为 **(账户, 方向, magic 族)** → 反向冷却互不影响。
- **Rule9 `_check_reverse_order`**（`rule_chain.py:322-333`）：接刀护栏**仅在 `reverse_order=True` 时才跑**；HEXP/live_override 正常路径 `reverse_order` 不置 True → 护栏不生效。
- **AI 解耦**：`ai.mode=decoupled`，AI 仅观测无否决 → 无第二道反向把关。
- **风险配置未写 Redis**（无 `hcm:config:risk*`）：跑代码默认 `max_pos=5 / cool_min=5 / score_pos_enabled=False` → 每方向每账户上限 5，双向合计可 10。

→ 结果：同账户同族可 BUY+SELL 并存并累加至 100 在仓（§1.3 实证）。

## 6. 修复方向（仅分析，待授权落地）

1. **给 live_override 补 per-bar 上限（修 D1）**：将 `:2840` 的例外收窄——live_override 也走 bar 幂等（或用 `last_live_trigger_bar` 强制 1 单/棒），仅保留 30s 限流作为棒间兜底。
2. **边沿去抖（修 D2）**：重新武装需满足"分值**持续**低于阈值 ≥ N 秒"或"方向翻转后稳定 ≥2 周期"，避免近门槛抖动反复触发；并对反向触发设最小间隔（如 `_trend_reverse_cooldown_seconds` 默认 90s 应同样约束 live_override 反向）。
3. **引入反向平仓/锁仓上限（修 D3/D4）**：在风控新增"同账户同族反向持仓上限"或"反向自动平旧"，打破只增不减。
4. **Rule9 默认生效（修 D5）**：正常路径也跑接刀护栏，或反向单强制走 `reverse_order` 分支。
5. **核实 D6 键名** + 把 `klines` 键名统一为 `open_time`。
6. **HEXP 频率治理（修 D8）**：评估 copy-trading 扇出账户数与每账户单量上限，避免自然节奏被放大成过量在仓。
