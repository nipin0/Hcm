# Magic=11 / 21 信号生成逻辑分析 + 优化方案

> 生成日期：2026-09-21
> 关联：`Magic11_21_频繁下单_链路缺陷分析_20260921.md`（缺陷清单 D1-D10）、`Magic21_多空共存_逻辑缺陷分析_20260921.md`
> 性质：**只读分析 + 优化设计草案**，未改动任何生产代码/配置（红线：写操作需显式授权）。
> 生产现状：`signal.active_model` 默认 `hexp`（`scheduler.py:6358`）→ HEXP(=11) 为主力信号源；live_override(=21) 为棒内实时/救援路径。

---

## 1. 信号生成逻辑全景

两族 magic 信号都经由同一出口 `_produce_signal()` 的 magic 赋值段：

`scheduler.py:4954-4989`
```python
_signal_mode = ("live_override" if live_override
                else (score_result.weight_scheme or "scoring")[:30])
_signal_magic = magic_for_signal_mode(_signal_mode)   # signal_publisher.py:48-82
# HEXP:Regime.* → 11 ； "live_override" → 21
magic = _signal_magic if final_direction in ("BUY","SELL") else 0
```

映射表 `signal_publisher.py:48-82`：`{hexp:11, scoring:12, live_override:21, range:55, state_osc:61, state_trend:62}`。

| 族 | 生成入口 | 触发节奏 | 幂等约束 | magic |
|---|---|---|---|---|
| **11 (HEXP)** | `_symbol_loop`→`_produce_signal`→`_hexp_engine.produce(live=False)`（`:3070`） | **每根 M5 bar 收盘 1 次** | 受 per-bar 幂等（`:2840` 走该分支） | 11 |
| **21 (live_override)** | 两源 → `_produce_signal(live_override=True)` | **棒内实时**，源②每 3s 轮询 | **绕过 per-bar 幂等**（`:2840` 例外） | 21 |

## 2. Magic=11（HEXP）生成逻辑详解

**路径**：`_symbol_loop`（`:1290`，每 bar 收盘调用 `:1332` `_produce_signal`）→ Step4 引擎选择（`:3045-3083`）：
```python
if active_model == "hexp" and _p4_hexp_on:
    score_result = await self._hexp_engine.produce(symbol, indicators, regime_result, live=False, ...)
```
→ `hexp_engine.py:1191 produce()` 判定 `direction/grade/passed` → `weight_scheme="HEXP:Regime.{NEUTRAL|TREND|RANGE}"` → magic 11。

**关键约束**：
- **per-bar 幂等闸门生效**（`:2840` 的 `if not (live_override or value_drive)` 分支）→ 同一 bar 仅产出 1 条 HEXP 信号，重复 bar 直接 `return`（`:2855-2865`）。
- 受 Step6 冷却（`scoring_engine.py:1630 compute_cooldown`）与 HEXP 自身 regime 闸门（`hexp_engine.py` 大量 `passed=False` 分支）节流。

**结论**：HEXP 生成侧**天然 ≤1 单/棒**，不存在棒内 spam。实测 25–36 单/天（见前序报告 §1.2）即其正常节奏。

## 3. Magic=21（live_override）生成逻辑详解

两个触发源，都调 `_produce_signal(live_override=True)`，共享 `state.last_live_override_time` 限流：

**源① `_live_override_loop`（`:1437`，每 5s）— adx_floor 救援**
- 仅当 `state.last_signal_blocked_by_adx_floor=True`（上根 bar 因 ADX 门槛被判 NO_TRADE）才激活。
- 实时 ADX≥floor 持续 30s + 限流 60s → 发 1 次救援。发射即复位 arming（`:1512-1514`）。
- 实测近窗口**休眠**（日志无 `Live override firing`），非主产源。

**源② `_live_score_publisher`（`:1576`，每 3s）— 边沿触发主产源**
- 用实时 bar 重算 `pre_score/direction`，C 层护栏（`:1687-1761`）：
  - 方向稳定 ≥2 周期(6s)（`:1597` `trigger_stable_required=2`）
  - **限流 ≥30s**（`:1596` `trigger_rate_limit_sec=30`，与源①共享 `last_live_override_time`）
  - **单棒单发**（`:1743` `last_live_trigger_bar==_cur_bar`）
  - **边沿触发**（`:1688-1691` 根治说明）：须"新上升沿"才发，防持续过阈反复产单。
- 触发条件（`1731-1761`）：方向∈(BUY,SELL) 且 `threshold_passed` 且 `live_edge_armed` 且稳定≥2 且非同棒已触发 且 非限流窗口 → 发单；随后 `:1762-1763` 复位 `live_edge_armed=False` 且记 `last_live_trigger_bar=_cur_bar`。

**关键风险点（决定"频繁"）**：
- `:2840` 对 `live_override` **跳过 per-bar 幂等** → 无 1 单/棒上限，仅靠 30s 限流 + 边沿。
- **边沿重武装过于敏感**（`:1737` 方向翻转、`1740` 分值回落门槛下 均 `live_edge_armed=True`）：近门槛抖动 / whipshaw 即反复重武装 → 每 30s 再触发、双向交替。
- 单棒单发**依赖 `klines[-1].get("open_time")`**（`:1696`、`:1743`）：键名不符/缺省 → `_cur_bar=None` → 该守卫静默失效（待核实键名）。

## 4. 评估：两族"频繁"成因诚实拆解（重要）

用户把 11、21 并列为"频繁下单"，但**两族成因不同，须区分**（避免一刀切改错方向）：

| 维度 | Magic=11 (HEXP) | Magic=21 (live_override) |
|---|---|---|
| 生成侧频率 | **≤1 单/棒**（幂等生效），25–36 单/天 | **棒内可多触发**，活跃日 22–39 单/天 |
| 是否真"高频" | 否（自然 bar 节奏） | **是**（绕过幂等 + 边沿敏感重武装） |
| "频繁感"来源 | copy-trading 扇出(1→多账户) + **持仓只增不减** | 生成侧本身过量 + 扇出 |
| 在仓叠加 | 42 单（BUY14/SELL28） | 58 单（BUY28/SELL30） |

**独立判断**：
- **Magic=21 是真正的生成侧缺陷**，应优先在信号塔修（补 per-bar 上限 + 边沿去抖 + 反向冷却联动）。
- **Magic=11 生成侧基本健康**；其"频繁"主要是**下游副作用**（扇出放大 + 无反向平仓导致累计）。若只在生成侧压 11 的单量，反而可能误伤正常策略节奏。**11 的治理重心应在风控/持仓层（反向敞口上限），而非生成节流。**

> 这与前序缺陷报告 D1/D2（21 高频）和 D3/D4/D8（共享下游）一致，但把"该改生成"与"该改下游"分清。

## 5. 优化方案（分层；生成侧给 file:line 具体改法）

### A. 生成侧（signal-tower，本次聚焦）

**A1. 给 live_override 补 per-bar 同向上限（修 D1）**
- 位置：`scheduler.py:2840` 例外收窄。
- 改法：live_override **仍允许棒内触发**（保留救援语义），但改为"每 (bar, 同向) 至多 1 单"：进入 `_produce_signal(live_override=True)` 前，检查 `state.last_live_trigger_bar==当前bar && state.last_live_trigger_dir==direction` → 跳过。保留**反向可再触发一次**（救援翻转），但要求反向冷却（见 A3）。
- 效果：消除同方向单棒内堆叠，保留翻转救援；21 的棒内频率从"每 30s"降到"每棒每方向≤1"。

**A2. 边沿去抖（修 D2）**
- 位置：`scheduler.py:1740`（分值回落即重武装）。
- 改法：重武装需"分值**持续**低于阈值 ≥ `edge_rearm_debounce_sec`（建议 15–30s）"，而非单 tick 回落即重武装。用 `state.last_below_threshold_since` 计时，消除近门槛抖动反复触发。

**A3. live_override 反向冷却联动（修 D2 双向交替）**
- 位置：`scheduler.py:1737` 方向翻转重武装处，或 Step6 `scoring_engine.py:1661-1662`。
- 改法：当 live_override 欲发**反向**于 `state.last_direction` 时，强制应用 `_trend_reverse_cooldown_seconds`（默认 90s，`:1858`）——即翻转后 90s 内不产反向单。与塔侧反转冷却口径一致，杜绝 BUY/SELL 秒级交替。

**A4. 单棒守卫去脆弱化（修 D6）**
- 位置：`scheduler.py:1696`、`1743`。
- 改法：不依赖 `klines[-1]["open_time"]` 字符串键；改用 `state.last_bar_open_time`（已对齐 bar 边界，`:2841`）或按 `now` 对齐 timeframe 计算的 bar 起点，保证守卫恒生效。

**A5. HEXP 生成侧"同向堆叠"可选护栏（仅兜底，非首选）**
- 位置：`_produce_signal` HEXP 分支（`:3070` 后 / Step8 前）。
- 改法（可选）：生成 HEXP 同向信号前，若本账户+本 magic 同向在仓已达阈值（如 risk.max_pos），则本棒降级为 NO_TRADE。
- **注意**：此条与风控 Rule4 重复，首选应修风控同向盲区（见 B1）；仅在风控上线前作临时生成侧兜底。

### B. 风控侧（rule_chain，治本，与生成侧并行）

**B1. 引入反向敞口上限 / 反向自动平（修 D3/D4）**
- `rule_chain.py:463-472` Rule4 限仓**只计同向**→ 新增"同账户同族反向持仓上限"或"同向达上限时反向单触发平旧"。
- 这是打破"只增不减、BUY+SELL 同存至 100 在仓"的根本手段，两族共享收益。

**B2. Rule9 默认生效（修 D5）**
- `rule_chain.py:322-333` `_check_reverse_order` 仅在 `reverse_order=True` 才跑 → 正常路径也评估接刀护栏，或反向单强制走 `reverse_order` 分支。

### C. 下游侧（copy-trading，治理放大）

**C1. 扇出单量治理（修 D8）**
- 评估 copy 跟随账户数与每账户单量上限；1 信号→N 账户使在仓翻倍，须与 A/B 协同设上限。

## 6. 风险与权衡（独立提示）

1. **A1 若误设"每棒 0 反向"会废掉救援语义**：须保留"反向可触发一次 + 反向冷却"，而非简单 1 单/棒。
2. **A2 去抖窗口过长会漏掉真实突破**：建议 15–30s，结合历史抖动幅度回测确定。
3. **A3 反向冷却 90s 在快速反转市会延迟入场**：可接受（救援本质是对已判 NO_TRADE 的补救，延迟优于锁仓）。
4. **B1 反向平旧是交易逻辑变更，影响 PnL**：须先在影子/回测验证，且需你拍板"是否允许有意对冲"——前序报告已提此决策点。
5. **A5 与 B1 重复**：避免两层都拦导致双保险变双误杀；B1 上线后撤 A5。
