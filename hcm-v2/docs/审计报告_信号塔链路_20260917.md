### A1 🔴 `hexp` 趋势启动放行被同函数末尾兜底**后写覆盖** [已核验]

**证据**
```python
# hexp_engine.py:2818-2819（放行）
sr.direction = _ts_dir
sr.threshold_passed = True
# hexp_engine.py:2937-2944（在 2818 之后，无条件执行）
if not _grade_ok:
    sr.threshold_passed = False
    sr.direction = "NO_TRADE"
# hexp_engine.py:437-438（序）
_GRADE_RANK = {"RED": 0, "C": 1, "B": 2, "A": 3, "S": 4}
# hexp_engine.py:421（登记默认）
"hexp.trend_start_min_grade": "ANY",     # → get(...,1) = rank 1
# hexp_engine.py:1962（对照）
_grade_ok = _GRADE_RANK.get(grade, 0) >= _min_rank
```

**根因**：`hexp.trend_start_min_grade="ANY"`（rank 1）比 `hexp.min_grade` 松（当 `min_grade` 高于 C 时），于是**"grade 未达 min_grade"这条注释明示的设计路径（`:2756`）被 2937 无条件回滚**，覆写只对"grade 达标但 direction=NO_TRADE"的**非设计路径**生效。

**危害**：趋势启动下单功能在目标场景下**永不生效**，且残留放行对象与设计意图相反（配置了却不生效）。

**优化方案**
- **P0-1（零风险，先做）**：加**一致性自检**——启动/热重载时比较 `rank(hexp.trend_start_min_grade)` 与 `rank(hexp.min_grade)`，前者更松即打 `WARNING`（不改变行为）。可观测化，避免"配了以为生效"。
- **P0-2（需用户拍板，改口径）**：二选一——
  - **方案甲（收紧语义）**：承认 `min_grade` 为硬顶，把 `hexp.trend_start_min_grade` 语义修正为"仅当 `>= min_grade` 时有效"，并同步注释/面板说明。**零代码风险**。
  - **方案乙（放行）**：在 `:2794` 块引入局部标志 `_ts_override_applied = True`，`:2937` 改为 `if not _grade_ok and not _ts_override_applied:`，使覆写豁免兜底；同时明确 `trend_start_min_grade` 是**独立第二门槛**。→ **触及下单口径，必须变更说明**。
- **推荐**：先做 P0-1（自检），用 7 天日志统计"趋势启动候选被 2937 回滚次数"，再据实选甲/乙。

**回退**：甲/乙均为局部改动，`git checkout` 单文件即可；自检可用开关关闭。
**验证**：日志出现 `trend_start_min_grade(...) looser than min_grade(...) — override will be reverted`；改后 `market_state_log` / signals 中出现 `hexp_trend_start_order` 的 BUY/SELL 即证明生效。

### A2 🔴 scheduler 三处把 `hexp` 的 NO_TRADE **翻回 BUY/SELL 并置放行** [已核验]

**证据**
```python
# scheduler.py:3024-3035  micro_state 补方向
elif (_cur_dir == "NO_TRADE" and _ms_dir in _ms_dir_map
      and _ms_state in (MicroState.REVERSAL, MicroState.TREND_PULLBACK)):
    score_result.direction = _new_dir
    score_result.threshold_passed = _force_pass      # :3032 默认 True
# scheduler.py:3057-3061  value_drive 注入
if _vworld in (1,-1) and _vscore > 0 and \
   str(getattr(score_result,"direction","") or "") in ("", "NO_TRADE"):
    score_result.direction = "BUY" if _vworld==1 else "SELL"
    score_result.threshold_passed = True
# scheduler.py:3223-3225  range_mr 注入
score_result.direction = _rng_dir
score_result.threshold_passed = True
score_result.range_mode = True
```

**根因**：三处注入的条件都是 `direction ∈ ("", "NO_TRADE")`，即**专门覆盖 hexp 的否决**；hexp 侧 12 道护栏（zone / cycle_pos / extreme_reversal / momentum_drain / momentum_flip / hurst / pullback / min_grade …）的结论**在下游不再有否决机会**。第 3 处还置 `range_mode=True`，使 `quality_gate` 把 AI 的 VETO 降级（见 A3）。

**危害**：同一信号被两个模块用不同门槛裁决（双裁决）；硬护栏被静默绕过（例如"极值接刀"被放行）。

**优化方案（最小侵入 + 显性化）**
- **核心思路**：把"**谁有权覆盖谁**"显性化。允许注入的**仅有软原因**，硬护栏一律不可覆盖。
- hexp 已把原因写入 `fallback_reason`（`hexp_engine.py:1968-1974`：`hexp_grade_below_min` / `hexp_no_direction` / `hexp_grade_red`；护栏各自写专属串）。故：
  1. 新增配置键 **`hexp.entry_gate.overridable_reasons`**（默认 `"hexp_no_direction"`，即**仅"hexp 本身就没方向"时可补方向**）。
  2. 三处注入前统一加守卫：`if not _is_overridable(score_result.fallback_reason): skip`。
  3. `range_mr` 注入同步受该守卫（当前无任何守卫）。
- **兼容性**：默认值等价于"只放行原本就无方向的信号"，比现状**更严**；如担心影响下单量，可先用配置把白名单扩到 `hexp_no_direction,hexp_grade_below_min`（热生效，秒级）。

**是否需要变更说明**：**需要**（触及"谁能最终决定方向"，属铁律二·系统核心规则）。
**回退**：把白名单配置为 `"*"`（或开关 `hexp.entry_gate.overridable_all=true`）即恢复现状，秒级热生效。
**验证（回归基线）**：改前记录 7 天 `signals.fallback_reason` 分布与 `hexp entry gate FILL` 日志条数；改后该计数应下降至仅"软原因"部分，且**方向不再出现与 hexp 硬护栏相反**的记录。

### B7 🔴 手数被**平方衰减**（`suggested_lot_ratio` 应用两次）[已核验]

**证据**
```python
# stream_consumer.py:210,255,262（第一次折算，写回 lot）
co_ai_mult = float(signal_data.get("suggested_lot_ratio", 1.0) or 1.0)
raw_lot = base * multiplier * (co_ai_mult if co_ai_mult > 0 else 1.0)
signal_data["lot"] = new_lot
# tools/mt5_bridge.py:1310,1313-1317（第二次折算）
_lot_ratio = float(signal_data.get("suggested_lot_ratio", 1.0) or 1.0)
if _lot_ratio not in (0.0, 1.0):
    lot = round(lot * _lot_ratio, 2)
```
**危害**：实际手数 = `base × tier × ratio²`。ratio=0.5（极值追单轻仓）→ 实际 **×0.25**；ratio=0.3（反手）→ **×0.09**。

**⚠ 修复前必须先补一步审计（不可直接改）**：需确认 `scheduler` 侧写入 `suggested_lot_ratio` 的**构成**（是否已含 `co_exec_lot_mult` / AI 倍率）。`stream_consumer.py:209` 注释称"scheduler 已将 co_exec_lot_mult 与 suggested_lot_ratio 合并进此字段"，但**该注释未附代码证据，属待验证**（铁律十二）。

**优化方案（确立"唯一折算点"，二选一）**
- **方案甲（推荐：折算点留在风控）**：`_apply_dynamic_lot` 计算 `raw_lot` 时**乘** `co_ai_mult`（现状），并在写回 `signal_data["lot"]` 的同一步，把 `signal_data["suggested_lot_ratio"] = 1.0`（标记"已折算"）。此后 `rule_chain` 在 evaluate 阶段的 ×0.5/×0.3 调整仍会写新值 → 桥的那一乘**只对后续调整生效一次**，不重复。
  - 风险点：`rule_chain` 的调整发生在 `_apply_dynamic_lot` **之后**（`stream_consumer.py:451` vs `455`），需确认其读取的是"当前 ratio"还是"塔原始值"。
- **方案乙（折算点留在桥）**：`_apply_dynamic_lot` **不乘** `co_ai_mult`（置 1.0），由桥统一乘。→ 改动更小，但会使"风控面板下发的 lot 值"与最终成交手数再次脱节（可观测性下降）。

**是否需变更说明**：**需要**（手数口径，属铁律二·核心公式）。
**回退**：`git checkout stream_consumer.py tools/mt5_bridge.py`；风控 `docker compose restart hcm-risk-engine`、桥 kill 由看门狗重拉。
**验证**：构造 ratio=0.5 的信号，断言成交 lot = `base×tier×0.5`（而非 ×0.25）；对比 `orders.lot` 与风控日志 `Dynamic lot: ... co_ai=`。

### B9 🔴 FSM 箱体"路径 B 解冻"未校验持仓 → **破界离场永久停发（孤儿单）** [已核验]

**证据**

**根因**：`:1087-1093` 的注释只为**路径 A** 补了 `positions_open <= 0` 护栏，**路径 B（计数变化解冻）未同步**。
