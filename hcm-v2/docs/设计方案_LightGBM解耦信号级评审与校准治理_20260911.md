## 0. 先纠正两个前提（避免方案建在错误诊断上）

| 常见预设 | 实测真相 | 证据 |
|---|---|---|
| "AI 评审太慢，需要毫秒级" | **评审本身已是毫秒级**（scheduler 同步 Redis GET，无网络调用）；真正的延迟与失误不在这里 | `scheduler.py:791`、`scheduler.py:2379` |
| "LightGBM 耦合太紧，要解耦" | **物理上早已解耦**（sidecar 独立进程，推理不阻塞下单）；真正的问题是**评审对象错位 + 分数无判别力 + 版本/校准失控** | `quality_scorer.py:2`；`ai_async_client.py:299-303` |

**本方案要解决的三个真问题**（全部有实测证据）：

1. **训练/推理对象错位（train/serve skew）**：标签按"每条信号"建（基准=信号 `entry_price`、方向=信号 `signal_dir`，`build_labels.py:207`），但推理是对"市场快照"打分——**信号的方向、entry、hp、grade 全都不是评审输入**（`quality_scorer.py:1591-1633` 主循环只读 K 线/快照）。模型答非所问，AUC=0.513 是必然结果。
2. **多头挂而未用**：方向头/买点头在生产**只观测、不参与裁决**（`direction_fuse=false`、`entry_fuse=false`，`quality_gate.py:383/405`）；而 UPGRADE 实测是反向指标（142 笔 −71.1）。
3. **校准与版本失控**：`calib_factor` **没有任何消费端**（死字段）；校准胜率标签来自被污染的 `orders.profit`（28.3% 回填伪 0，`signal_publisher.py:706-764`）；版本号"拒收也占号"（`auto_retrain.py:1174-1176`）→ 30 天 35 版。

## 1. 目标与非目标

### 1.1 目标
1. 信号塔每产一条信号，**针对这条信号**做一次 LightGBM 评审（输入含信号属性 + 当时市场特征），**亚毫秒级**，评审合格才进入发布/风控/下单。
2. 方向头与买点头**接入裁决**，与质量头整合为一个可解释的评审分。
3. 校准机制"离线 OOF 随模型工件 + 在线滚动贴合行情"双层设计，校准质量纳入上线闸门。
4. 版本治理：staging → 验收 → canary → promote，终结版本抖动。

### 1.2 非目标（铁律边界，明确不做）
- **AI 无独立开仓权**（铁律 5.1）：评审只有 **PASS / DOWNGRADE / VETO** 三档；"评审合格后触发下单"的语义 = **放行信号塔已产出的信号**，AI 自己不产生信号、不反向开仓。
- 不改 hexp 原始信号方向（铁律五.1）；不改异步架构（铁律五.2）；不删减超时/重试/熔断/降级（铁律五.3）。
- 不引入在线学习/实时训练；不碰 DeepSeek 链路（维持现状仅观测）。

## 2. 总体架构（Before / After）

### 2.1 Before（现状，问题标注）
```
sidecar quality_scorer.py（每5s，市场快照）
  └─ 36维市场特征（无信号属性）→ 三头打分 → Redis hcm:live:hexp:ai:{sym} (TTL15s)
scheduler._produce_signal（每根 M5 bar）
  └─ hexp 评分 → Redis GET 快照分 → quality_gate（方向/买点头未接线）
       → VETO 不落库 → publish → 风控 → 桥
auto_retrain（24h + PSI硬触发无去抖）→ 版本+1（拒收也占号）→ 直接双写上线（无canary）
calibration_daily（标签源=orders.profit 污染表）→ calib_factor → 【无消费端】
```

### 2.2 After（目标架构）
```
sidecar quality_scorer.py（角色降级为"特征生产者"，保留全部现有职责）
  └─ 每 bar 收盘：36维市场特征快照 → Redis hcm:feat:m5:{sym}:{bar_time}（TTL 20min）
       + 健康监控/inference_log/漂移防御（现状全部保留，不动）

【新增】信号级评审器 Reviewer（scheduler 进程内，in-process LightGBM，亚毫秒）
  scheduler._produce_signal：
    hexp 评分 → 构造 ReviewInput（信号属性 + 特征快照）
      → Reviewer.review()（三头 predict + 校准 + 整合公式 + 阈值裁决）
      → PASS / DOWNGRADE / VETO → gate_decision 全量落库（含 VETO）
      → publish → 风控 → 桥（不变）

【新增】训练/治理管线（staging → 验收 → canary → promote）
  build_review_labels（信号级标签，K线触达，不碰 orders.profit）
    → train_review_model（三头，时序 CV，OOF isotonic）
    → staging 目录落盘（不占版本号）
    → 验收闸门（OOF AUC≥0.55 + 分层单调 + ECE≤阈值 + 样本量）
    → shadow ≥24h（只记录不拦截）→ canary（只 DOWNGRADE）→ promote（人工确认）
    → 在线滚动重校准（只重拟合 isotonic，不动模型权重）
```

**关键架构决策：评审器放在 scheduler 进程内（in-process），不是新服务。**
- LightGBM Booster 单行 36 维 predict 是**亚毫秒级**纯计算，无需独立服务；
- 模型文件经 bind-mount 的 `tools/models/` 目录读取，热加载沿用 sidecar 已有的 mtime 指纹模式（`quality_scorer.py:1497-1513`）；
- 校准器用纯 numpy 的 `NumpyCalibrator`（`tools/calib_np.py`），**生产容器无 sklearn 也能加载**——这是已有产物，直接复用；
- 需要 signal-tower 镜像增加 `lightgbm` 依赖（仅 predict，无训练）。

## 3. 评审机制设计（需求①）

### 3.1 评审输入契约 ReviewInput
| 组 | 字段 | 来源 |
|---|---|---|
| 信号属性 | `signal_id, symbol, direction, entry_price, sl_price, tp_price, hp_score, grade, signal_mode, session, regime` | scheduler 构造 SignalData 时已有（`scheduler.py:3368`） |
| 市场特征 | 36 维契约特征（`_model_feature_cols.py:51-146`） | sidecar 每 bar 快照 `hcm:feat:m5:{sym}:{bar_time}` |
| 衍生量 | `sl_dist_atr = |entry−sl|/atr14`、`tp_dist_atr`、`rr_designed`、`dir_sign` | 评审器内现算（纯算术） |

**新鲜度**：特征快照 `bar_time` 必须与信号 bar 同根（M5 容差 1 根）；缺失/过期 → 走降级链（§3.4）。

### 3.2 评审输出契约 ReviewVerdict
| 字段 | 说明 |
|---|---|
| `action` | `PASS / DOWNGRADE / VETO`（**无 UPGRADE**，见 §4.3） |
| `review_score` | 整合评审分 ∈[0,1]（已校准） |
| `dir_prob / dir_pred / entry_prob / quality_prob` | 三头原始输出（归因用） |
| `reason_codes` | 如 `DIR_CONFLICT / LOW_ENTRY / LOW_QUALITY / FEAT_STALE` |
| `model_version / calib_version` | 版本追溯 |
| `latency_ms` | 评审耗时（自证毫秒级） |

### 3.3 裁决公式（全部配置化，无硬编码）
```
# 第一层：方向一致性（方向头唯一硬用途）
dir_conflict = (dir_pred 与 signal.direction 相反) 且 (dir_prob ≥ ai.review.dir_conflict_prob)
  → action = VETO 或 DOWNGRADE（由 ai.review.dir_conflict_action 决定，默认 DOWNGRADE）

# 第二层：整合评审分（买点头 + 质量头）
review_score = w_e · entry_prob + w_q · quality_prob        # w_e+w_q=1，默认 0.6/0.4
  （方向一致时方向头不加分——它只负责"挡反向"，不负责"抬分"，避免重蹈 UPGRADE 反向覆辙）

# 第三层：阈值裁决
review_score < ai.review.veto_floor        → VETO     （默认 0.15，沿用现状语义）
review_score < ai.review.pass_threshold    → DOWNGRADE（默认 0.45，可离线标定）
其余                                      → PASS
```

### 3.4 降级链（铁律五.3，逐级显式）
| 故障 | 行为 | 配置键 |
|---|---|---|
| 模型文件缺失/加载失败 | 纯 HEXP 放行（pass_through），记 `MODEL_MISSING` | `ai.review.fallback=pass_through`（默认） |
| 特征快照缺失/过期 | pass_through，记 `FEAT_STALE` | 同上 |
| 特征缺失率 > 阈值 | pass_through，记 `FEAT_MISSING` | `ai.review.max_feat_missing=0.3` |
| 评审耗时 > 硬超时 | pass_through，记 `TIMEOUT` | `ai.review.timeout_ms=50` |
| 校准器退化（档位<8） | 退用 raw 概率（沿用 `calib_blend_w` 机制，`quality_scorer.py:963-967`） | `ai.review.calib_min_levels=8` |

**预算**：特征读取（本地缓存/1 次 Redis GET）+ 单行 predict ≈ **<5ms**，硬上限 50ms。桥的 180s 陈旧闸（`mt5_bridge.py:65-70`）留出的预算极其充裕——"毫秒级"诉求被满足且有数量级余量。

### 3.5 观测与归因（修现状黑洞）
- **`gate_decision` 全量落库，含 VETO**：现状 VETO 信号不落库（`scheduler.py:2428-2431`），导致"被 AI 拦掉的信号后来该不该拦"无法回算——这是评审机制迭代的第一数据资产，**必须修**。
- 每次评审写 `hcm_ai.review_log`：ReviewInput 摘要 + ReviewVerdict 全字段 + 特征快照 bar_time。
- 事后命中回算：每日任务按 K 线触达口径（同 build_labels）回算 VETO/DOWNGRADE/PASS 各档的"若放行会怎样"，产出评审分层报表。

## 4. 多头整合设计（需求②）

### 4.1 三头职责重新划定（治"挂而未用"）
| 头 | 现状 | 新职责 | 依据 |
|---|---|---|---|
| 方向头 | `direction_fuse=false` 只观测 | **唯一硬闸**：挡"信号方向与模型方向强冲突" | 方向头标签是未来 24 根 M5 的 ±0.8·ATR（`build_labels.py:292-298`），天然是方向判据 |
| 买点头 | `entry_fuse=false` 只观测 | **评审分主权重**（w_e=0.6）：判"这个点位能不能进" | 标签=12 根内 1R 先到（`build_labels.py:310-377`），正是"入场时点"判据 |
| 质量头 | 当前唯一在用的分 | **评审分辅权重**（w_q=0.4）+ 手数档参考 | 与买点头同族但口径更宽 |
| 状态头 | 仅诊断 | 维持仅诊断，不进评审分 | `train_signal_quality.py:330-333` |

### 4.2 精准判断的两个前置修复（不修则多头无意义）
1. **消灭 train/serve skew（本方案核心）**：训练样本的特征集 = §3.1 评审输入契约（含信号属性），训练与推理严格同源。当前模型在生产上的 AUC（0.513）测的是"市场快照"任务，**不等于信号级模型能达到的水平**——信号级模型需要重训后重新验收，不能拿 0.513 直接否定 LightGBM 技术路线。
2. **统一标签口径**：质量头 R 用 `atr_fallback`（`build_labels.py:163-164`）而买点头用真实 SL 优先（`:325-326`）——两头在同一信号上学不同的"R"，整合时量纲不一致。**统一为：真实 SL 优先，ATR 兜底**，两头一致。

### 4.3 UPGRADE 下线
实测 UPGRADE 142 笔 −71.1、高置信反例 4 笔全为 UPGRADE（−68.06）。**新评审器不设 UPGRADE 档**；`ai.review.upgrade_enabled` 键保留但默认 `false` 且代码路径删除（铁律十三：新增与删除成对）。

## 5. 校准机制设计（需求③）

### 5.1 双层校准架构
| 层 | 机制 | 频率 | 产物 |
|---|---|---|---|
| **离线层**（随模型） | TimeSeriesSplit OOF 汇总拟合 isotonic（9/10 已落地，保留） | 每次训练 | `calib_review_vN.pkl`（NumpyCalibrator，与模型同版本原子切换） |
| **在线层**（贴合行情） | 用 review_log 的预测分 vs K 线触达真实结果，滚动窗口重拟合 isotonic | 每日 1 次（样本 ≥ `ai.review.recalib_min_samples` 才执行） | `calib_review_vN_rM.pkl`（只换校准器，不动模型权重） |

### 5.2 在线层的四个硬设计（对照实测失效根因）
| 现状失效根因（侦察实证） | 新设计 |
|---|---|
| 校准胜率标签来自 `orders.profit`（28.3% 伪 0 → 全标 loss，`signal_publisher.py:706-764`） | **标签只用 K 线触达**（与 build_labels 同口径），永不碰 orders 盈亏字段 |
| 累计窗口 UNBOUNDED PRECEDING（`signal_publisher.py:820-824`），旧脏数据永久稀释 | **滚动窗口**（默认 20 个交易日，配置化 `ai.review.calib_window_days`） |
| 胜率锚 0.5 vs 真实基线 ~20.8%（`local_calibrator.py:65`） | isotonic 无锚，单调拟合；样本 < 阈值不重校准 |
| 校准质量不进采纳闸门（`auto_retrain.py:1299-1327` 只看 AUC） | **ECE + 可靠性单调性 + 档位≥8 进验收闸门**，不达标不 promote |
| `calib_factor` 无消费端（死字段） | **删除 `co.calib.*` 写回链与 calibration_daily 报表链**（铁律十三），评审校准统一走 review_log |

### 5.3 校准健康监控（每日报表，只读）
- Brier score、ECE、10 分桶"预测胜率 vs 实测胜率"可靠性表；
- 校准漂移告警：近 7 天 ECE > `ai.review.ece_alert`（默认 0.08）→ 触发一次在线重校准（**不是**全量重训）；
- 该报表同时是方向头/买点头的分层单调性看板（验收门槛的日常化）。

## 6. 版本治理（治"30 天 35 版"）

### 6.1 四态生命周期
```
TRAIN（随时可跑，产物落 staging/，不占版本号）
  → ACCEPT（验收闸门通过才分配正式版本号 vN，promote 到 models/）
  → SHADOW（≥24h 或 ≥200 条信号，只记录不拦截，与 champion 同输入对比）
  → CANARY（只开 DOWNGRADE，不开 VETO，≥3 天）
  → ACTIVE（全量，含 VETO；champion 保留一键回切）
```

### 6.2 验收闸门（全部硬性，不达标即拒）
| 项 | 门槛 | 现状对照 |
|---|---|---|
| OOF AUC（买点头/质量头） | ≥ 0.55 | 现网快照级 0.513 |
| 方向头 C 口径 dir_hit | ≥ 0.55 | — |
| 分层单调性 | 10 分桶胜率与分数 Pearson > 0 | 现网 **−0.428** |
| 校准 ECE | ≤ 0.05 | 现网校准器曾把 0.302 压到 0.05 |
| 校准档位 | ≥ 8 | `CALIB_MIN_LEVELS=8` 已有 |
| 最小样本 | 训练 ≥ 2000，OOF 正样本 ≥ 200 | — |

### 6.3 治抖动三条
1. **版本号只在 ACCEPT 时分配**——staging 产物被拒不占号（修 `auto_retrain.py:1174-1176` 的"先占号后验收"）。
2. **触发去抖**：PSI 硬触发后 24h 冷却；校准漂移优先走"在线重校准"而非全量重训。
3. **promote 需人工确认**：`ai.review.auto_promote=false`（默认）→ shadow/canary 报表出来后由你拍板切换；切换 = `config_provider.set` 双写（铁律 5.2），回切 = 指回上一版本路径（保留最近 3 版，`KEEP_MODEL_VERSIONS=3` 已有）。

## 8. 六段权衡（铁律七 · C 类提案强制）

### 8.1 收益
- 评审对象从"市场快照"变为"信号级"，消灭 train/serve skew——这是让 LightGBM 有机会达到 AUC≥0.55 的**结构性前提**；
- 方向/买点头从"挂了不用"变为"各司其职"，多头信息真正进入裁决；
- 校准双层 + 验收闸门，分数从"不可信的数"变成"可解释的概率"；
- 版本四态 + 人工 promote，终结 30 天 35 版的抖动；
- VETO 全量落库 + 事后回算，评审效果首次可度量、可迭代。

### 8.2 风险
| 风险 | 缓解 |
|---|---|
| 信号级模型重训后仍不达标（AUC<0.55） | 验收闸门卡住不 promote，系统停留在 shadow/纯 HEXP，**零实盘影响**；这是"花一次训练成本买一个确定性答案" |
| scheduler 进程内加载模型引入新故障点 | 降级链全部 pass_through；模型加载失败=纯 HEXP（与今天 `max_age_sec` 失效时行为一致，已验证安全） |
| 样本量不足（HEXP 信号量有限） | 标签可回溯历史 signals 全量（`build_labels.py:543-556` 同法），门槛设 2000 条，不足则不启动 promote |
| 特征快照管道（新 Redis 键）增加 sidecar 职责 | sidecar 本就每 5s 算全量特征，只是多一次 SET；TTL 20min 可控 |
| 校准在线层引入新的"自动改参数"路径 | 每日最多 1 次、样本门槛、只换校准器不换模型、全程落库可回滚 |

### 8.3 兼容性
- 新模式与 coupled 并存，`ai.review.enabled=false` 时行为与今天**完全一致**；
- sidecar、DeepSeek、风控、桥全链路零改动；
- 信号契约/payload 不变（评审结果只进 gate_decision/review_log，不进 stream 字段）。

### 8.4 回退
- 任一阶段：`ai.review.enabled=false` 或 `mode=shadow` 秒级回退（config_provider PUB 即时生效）；
- 模型回切：指针指回上一版本（保留 3 版）；
- 代码回滚：bind-mount 源码 git 回退 + 容器重启（signal-tower 单容器，爆炸半径可控）。

### 8.5 监控
- 新增每日评审报表：三头分档命中率、评审分层（VETO/DOWNGRADE/PASS 的事后命中）、校准可靠性表、版本对比（champion vs candidate）；
- 告警：评审延迟 P99 > 50ms、特征快照缺失率 > 5%、ECE 超阈、降级链触发率 > 1%。

### 8.6 排期（每阶段独立可停）
| 阶段 | 内容 | 产出 | 实盘风险 |
|---|---|---|---|
| **P0 数据卫生** | 修 gate_decision VETO 落库；删 calibration_daily 死链；review_log 建表 | 可观测性基线 | 零（只加表/日志） |
| **P1 训练管线** | build_review_labels（信号级+统一 R 口径）+ train_review_model + OOF 校准 + 验收闸门 | 离线验收报告 | 零（纯离线） |
| **P2 评审器 shadow** | scheduler 内 Reviewer（shadow 模式）+ 特征快照管道 + 每日对比报表 | shadow vs 现状对比数据 | 零（只记录不拦截） |
| **P3 canary** | 只开 DOWNGRADE ≥3 天 | canary 报表 | 低（仅降级，不拦单） |
| **P4 active + 治理** | 全量评审 + 在线滚动校准 + 版本四态落地 | 全量运行 | 中（VETO 生效，有一键回退） |

**硬性顺序**：P1 离线验收不达标 → 不进入 P2；P2 shadow 数据不显著优于现状 → 不进入 P3。每一步都是"先用数据证明，再扩大权限"。
