### 1.2 口径声明（重要）
本报告**不采用**"美元盈亏比"作为唯一判据，同时给出**与手数无关的 R 倍数口径**。原因：美元口径可能被手数/仓位管理差异污染（本次已实测排除）。

R 倍数定义（价格口径，可跨账户比较）：
```
risk   = |open_price − sl|                  # 初始风险（价格距离）
mv     = (close − open) × dir_sign          # 有向位移
实际R  = mv / risk
完成度 = mv / |tp − open|                   # 目标兑现比例
```
样本限制：R 口径仅覆盖 `sl > 0` 的 1168 笔（占 69.4%）。

## 3. 核心发现一：「赚小」的机制链（一级根因）

### 3.1 ★ 组平守卫 TAIL-STOP-GUARD：10/10 次在整组浮盈时平仓 `[实测]` `[代码]`

**代码位置**：`tools/mt5_bridge.py:5440-5560`（函数 `_tail_stop_guard`）

**触发条件**（代码原文逻辑）：
1. 同一 `(symbol, direction)` 组内 **≥ 2 仓**
2. 组内 **≥ 1 笔已保本**（`sl ≥ entry − tol`）
3. **尾单**（ticket 最大 = 最新开仓）浮亏 **> `close.tail_stop_atr_mult` × ATR**
4. → **全平该同向组**（不只平尾单）

**生产参数真值** `[实测]` Redis `hcm:config:v2`：
| 键 | 生产值 | 代码默认值 | 差异 |
|---|---|---|---|
| `close.tail_stop_enabled` | `True` | — | 启用 |
| **`close.tail_stop_atr_mult`** | **`0.2`** | `0.5` | **被收紧到 40%** |
| `close.tail_stop_cooldown_sec` | `60` | `60.0` | 一致 |

**归因表逐笔实测（`hcm_ai.tail_close_attribution`，全部 10 条）**：

| id | 时间(UTC) | 组内仓数 | 尾单浮亏(ATR) | **整组浮动盈亏** | 组内最大浮盈单 |
|---|---|---|---|---|---|
| 1 | 09-04 17:40 | 2 | 0.243 | **+15.65** | +16.79 |
| 2 | 09-04 18:03 | 3 | 0.268 | **+6.59** | +5.50 |
| 3 | 09-07 06:18 | 2 | 0.214 | **+2.36** | +3.55 |
| 4 | 09-07 07:37 | 2 | 0.214 | **+1.08** | +2.05 |
| 5 | 09-07 09:10 | 2 | 0.332 | **+7.65** | +8.97 |
| 6 | 09-07 15:41 | 2 | 0.369 | **+0.19** | +1.62 |
| 7 | 09-08 19:31 | 2 | 0.264 | **+2.66** | +4.16 |
| 8 | 09-08 19:56 | 3 | 0.236 | **+11.39** | +9.07 |
| 9 | 09-08 22:45 | 2 | 0.203 | **+0.98** | +1.79 |
| 10 | 09-10 11:50 | 2 | 0.217 | **+1.82** | +3.02 |

**关键读数**：
- **10 次触发，整组浮动盈亏全部为正**（+0.19 ~ +15.65），累计 **+50.37**。
- 触发时尾单平均只浮亏 **0.25×ATR ≈ 1.1 USD**，却把整组平掉。
- 典型 id=1：组内 409560540 已浮盈 **+16.79**（SL 已抬到 4422.94，锁定 13.4 USD），为"保护"另一笔 −1.14 的尾单，**两笔一起平**。

> **机制解读（这是"赚小"的放大器）**：该守卫的语义是"同向加仓组的尾部保护"，但它把"尾单 0.2×ATR 的浮亏"当作**趋势反转信号**，去平掉**整组**——包括那些 SL 已经上移、正在趋势中奔跑的仓位。因为"组内有保本单"是常态（保本门槛仅 1.0×ATR，见 §3.2），**该守卫几乎处于"随时可武装"状态**。等效于把组内所有仓位的盈利天花板压到"第一次 0.25×ATR 级回撤"。
> **`[推断]` 未证实部分**：本次未做反事实回测（若不平仓，这些组最终盈亏如何）。因此**不能断言这 10 次一定是净损失**——但"整组浮盈时被平"这一事实本身与"赚小"方向一致，且强度足够支撑立即核查该参数。

### 3.2 保本门槛与 TP 距离的结构性矛盾 `[代码]` `[实测]`

**代码位置**：`tools/mt5_bridge.py:5139-5148`
```python
# 有效保本门槛 = min(be_trigger=breakeven_atr_mult×ATR, TP距×breakeven_tp_ratio)
_be_trig = min(be_trigger, _tp_dist * breakeven_tp_ratio)
_be_trig = max(_be_trig, 1.0)
_trail_start_eff = min(trail_start, _tp_dist * trail_start_tp_ratio)
```

**生产参数真值** `[实测]`：
| 键 | 生产值 | 含义 |
|---|---|---|
| `close.breakeven_atr_mult` | `1` | 保本门槛 1.0×ATR |
| `close.breakeven_tp_ratio` | `0.5` | 或 TP 距的 50%，取小 |
| `close.trail_start_atr_mult` | `2` | 移动止盈启动 2.0×ATR |
| `close.trail_start_tp_ratio` | `0.5` | 或 TP 距的 50%，取小 |
| `close.max_sl_atr_mult` | `1.8` | SL 距离硬上限 |
| `close.tp_relay_enabled` | 空（走默认 `True`） | **TP 接力外推** |

**结构性矛盾（按典型值推导）**：
```
SL 距 ≈ 1.8×ATR（上限）
设计 R:R 中位 1.506  →  TP 距 ≈ 2.71×ATR
保本门槛 = min(1.0×ATR, 2.71×ATR×0.5) = 1.0×ATR
移动止盈启动 = min(2.0×ATR, 1.355×ATR) = 1.355×ATR
```
→ **价格只要走到 1.0×ATR 盈利（= TP 距的 37%），SL 就被抬到 entry+0.15×ATR；此后任何 0.85×ATR 的回撤即把单子扫成"保本微利单"。而要走完 TP 需要"零 0.7×ATR 级回撤"地推进 2.71×ATR。**

**实测验证** `[实测]`（赢单 693 笔，TP>0）：
| 指标 | 值 |
|---|---|
| 目标完成度 中位 | **0.133**（即平均只兑现止盈目标的 13.3%） |
| 完成度 P25 / P90 | 0.080 / 0.640 |
| 完成度 ≥ 0.8 的赢单 | **44 笔 / 693 = 6.3%** |
| 完成度 ≥ 0.5 的赢单 | 113 笔 / 693 = 16.3% |

**赢单 R 分布** `[实测]`（711 笔有 SL 赢单）：
| 区间 | 笔数 | 占比 |
|---|---|---|
| `0 < R < 0.3`（保本/微利被扫） | **318** | **44.7%** |
| `0.3 ≤ R < 0.8` | 73 | 10.3% |
| `R ≥ 0.8`（像样的赢单） | 320 | 45.0% |

### 3.3 分批止盈完全缺失 `[实测]` `[代码]`
| 项 | 状态 | 位置 |
|---|---|---|
| `close.partial_close_enabled` | **`False`** | Redis 生产值 |
| `close.partial_close_ratio` | **`0`** | Redis 生产值 |
| 信号塔 `tp2` 字段 | **恒为 `0.0`**，三处写死 | `scheduler.py:3330 / :3495 / :3940` |

> **结论**：系统**没有任何"到 1R 平一半"能力**。赢单只有两种命运：被保本/组平扫成微利，或极少数（6.3%）走完 TP。

### 3.4 TP 接力的反作用 `[代码]`
`close.tp_relay_enabled` 默认 `True`，代码 `mt5_bridge.py:5169/5196`：价格过了 trail_start 后，**TP 随现价继续外推**（只进不退）。
→ 在"保本门槛 1.0ATR、行情走不完 2.71ATR"的背景下，把 TP 继续推远，**进一步降低达成概率**。这两个机制方向相反，属于**逻辑冲突**。

### 4.1 击穿止损的单笔杀伤 `[实测]`

### 4.3 ⚠️ 重要修正：38 笔 `sl=0` **不能断言为真实裸仓**

审计过程中曾得出的"38 笔绕过信号塔的无止损裸单"结论，经复核**证据不足**，理由如下：

| 证据 | 内容 | 指向 |
|---|---|---|
| `[代码]` | `position_sync.py:975-983` 回填 INSERT 写的是 `r["sl"], r["tp"]`（对账快照字段），**并未调用 MT5 `history_orders_get` 取原始 SL/TP** | 回填行的 `sl` 不可信 |
| `[实测]` | 38 笔全部 `trail_state IS NULL`、`created_at = updated_at` | 均为**纯回填 INSERT**，从未被移动止损管线管理 |
| `[实测]` | 桥日志近 168 小时 `init SL` 补挂日志 **0 次**、无任何无 SL 告警 | **近 7 天不存在需要补挂止损的真实裸仓** |
| `[实测]` | `hcm_trading.positions` 表 SL 覆盖 2265/2316 = **97.8%** | 活仓几乎都有 SL |
| `[实测]` | 下单链路正常：512 笔在途单 SL 覆盖 **100%**；1589 笔有 `signal_id` 的单 SL/TP 覆盖 **100%** | 下单环节没有丢 SL |

**修正后的表述**：38 笔 `sl=0` 是**记账层面的缺字段**（对账回填路径未取 MT5 真值），其 −238.78 的**盈亏是真实的**（来自 deals），但**"是否无止损"这一属性无法从 PG 单侧证实**。
→ 由此，**"阻止外部裸单"不应作为第一优先级方案**；真正的第一优先级是 §3 的"赚小"机制，以及先修好记账口径（§5.3）。

### 4.4 无止损补挂当前被"总闸"耦合 `[代码]`
`mt5_bridge.py:5152-5157`：无 SL 仓的初始宽保护 `new_sl = tick.bid − initial_distance` **只在 `_update_trailing_stops()` 内**，而整个函数被 `close.trailing_stop_enabled` 门控（`mt5_bridge.py:5040-5042`）。
→ **一旦移动止损总闸被关，"无 SL 必补"护栏同时失效**。这是一个独立缺陷：**"补挂止损"是风控刚需，不应与"移动止损"共用开关**。

## 6. LightGBM 复核下单的可信度评估

### 6.1 结论：**当前不可信，不应作为下单闸门** `[实测]`

| 检验 | 结果 | 判读 |
|---|---|---|
| 订单级 `c_ai` AUC（是否盈利） | **0.5131**（n=421，赢273/亏148） | ≈ 抛硬币（0.5） |
| 剔除 backfill/sync 后 AUC | **0.4859**（n=141） | **低于 0.5，方向都是错的** |
| 方向头 `ai_dir_prob` AUC | **0.507**（n=391） | 无判别力 |
| 三种 JOIN 口径交叉验证 | 均为 **422** 笔 | 样本数稳健，不是口径问题 |
| AUC 用纯 SQL 秩和公式独立复算 | 0.5131 | 与模型侧一致 |

> **AUC 的读法**：0.513 意味着"给一笔盈利单和一笔亏损单，AI 分数正确排序的概率只有 51.3%"。作为"复核下单"的判据，**它提供的信息量约为 0**。

### 6.2 分层单调性：方向反了 `[实测]`
| action | 笔数 | 合计 PnL | 判读 |
|---|---|---|---|
| `UPGRADE`（AI 看好，升级/加仓） | 142 | **−71.1** | **反向指标** |
| `DOWNGRADE`（AI 看衰，降级） | 234 | **+31.7** | AI 看衰的反而赚 |
| 高置信反例（`c_ai ≥ 70` 且 `profit ≤ −10`） | **4** | **−68.06** | 全部为 `UPGRADE` |

分层与胜率的相关性（前次复核）：**Pearson = −0.428**（**负相关**）——桶序越高，胜率越低。

### 6.3 AI 样本 vs 未复核样本 `[实测]`
| 组 | 笔数 | PnL | 胜率 | 赢均 | 亏均 | RR |
|---|---|---|---|---|---|---|
| AI 已复核 | 422 | **−48.14** | 64.7% | 4.131 | −7.892 | 0.523 |
| 未复核（同期） | 154 | **+129.81** | 75.3% | — | — | — |

> **`[推断]` 这是否构成"AI 有害"？不能直接下此结论。** 两组的时间窗与选单机制不同，存在**选择偏差**，不能当因果。但结合 §6.1 的 AUC 0.513 与 §6.2 的反向分层，**"AI 复核不提供有效信息"这一结论是稳固的**。

### 6.4 模型版本抖动（治理缺陷） `[实测]`
| 指标 | 值 |
|---|---|
| 近 30 天 distinct `model_version` | **35 个** |
| 单日最多并行版本 | **2026-08-31：14 个并行**（23629 行） |
| v92 | 09-04 23:55 ~ 09-09 07:31（60604 行） |
| v97 | 09-09 07:31 ~ 09-10 10:44（26081 行） |
| **v103**（当前线上） | **09-10 10:44 ~ 13:52（仅约 3 小时，3055 行）** |

> **关键影响**：`c_ai` 的 AUC 是**跨 35 个版本混合**算出的。**版本抖动本身就是 AUC 失效的重要原因之一**——不同版本的分数不可比，混在一起做统计没有意义。这也意味着 §6.1 的负评级在**任何单一版本上尚未被单独验证**。
> 另：9/10 当日刚发生质量头契约变更（降至 36 维，方向/买点头切 v104），**当日样本不可用于评估**。

### 6.5 校准器失效 `[实测]`
`calibration_daily.calib_factor` 与实际胜率的相关性仅 **0.138** → 校准因子已不反映真实概率。

## 8. 「赚小亏大」解决方案

> **实施原则**：所有写操作（改 Redis / 改代码 / 重启容器 / 写 PG）**均需逐项显式授权**。本报告只给出方案与依据。

### 阶段 A｜零代码、当天可验证（**建议先做，成本最低、证据最强**）

| # | 动作 | 依据 | 风险与建议 |
|---|---|---|---|
| A1 | `close.tail_stop_atr_mult`：**0.2 → 0.5**（或先 `close.tail_stop_enabled=False` 观察） | §3.1，10/10 次整组浮盈被平 | 关闭后组内深回撤不再保护 → **建议先调到 0.5 而非直接关**，观察 3 天整组盈亏分布 |
| A2 | `close.breakeven_atr_mult`：**1.0 → 1.5** | §3.2，保本门槛卡在 1.0ATR = TP 距 37% | 回撤容忍度上升，单笔风险略增；**配合 A3 一起改** |
| A3 | 缩短 TP 或降低 `close.tp_max_atr_mult` / 提高 `close.tp_min_atr_mult`，让设计 R:R 落到 **1.0~1.2** | §3.2，完成度中位 0.133（TP 太远） | **必须回测验证**，不可拍脑袋 |
| A4 | `close.tp_relay_enabled`：**True → False**（先关掉 TP 外推） | §3.4，方向冲突 | 会在原 TP 处平仓，损失"趋势延续"收益；**建议与 A3 二选一，用回测对比** |
| A5 | 修正 `close.break_even_enabled` 幽灵键（接线或从面板移除） | §7 P0 | 纯治理，无交易风险 |
| A6 | 核查 `detect_mt5_tz_offset` 双轨偏移 | §7 P3 | 纯治理 |

**A 阶段的验证方法**：改动后按"整组盈亏 / 赢单完成度中位 / R<0.3 占比"三项指标对比改前 7 天基线（本报告 §3.2 的 0.133 / 44.7% 即基线）。

### 阶段 B｜结构性改造（需开发 + 回测）

| # | 动作 | 目标 |
|---|---|---|
| B1 | **组平守卫改为"只平尾单，不平整组"**，或至少加"整组浮盈 > 0 时不触发"前置条件 | 消除 §3.1 的连坐 |
| B2 | **启用分批止盈**：`close.partial_close_enabled=True` + 到 1R 平 50%，剩余交给 trail | 让 44.7% 的微利单至少兑现半个目标 |
